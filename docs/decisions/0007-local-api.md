# 0007. Локальний API: токен для всіх ендпоінтів, обов'язковий `Idempotency-Key` у БД, loopback-origins

- **Дата:** 2026-10-29
- **Статус:** прийнято (підтверджено власником проєкту 2026-10-29 під час планування T0.7)
- **Зачеплені розділи ТЗ:** §14, §15, §16
- **Зачеплені задачі:** T0.7, T6.1, T6.2, T6.3, T6.4, T6.7, T5.10

## Контекст

ТЗ §14 вимагає для локального API «bearer-токен для UI, перевірку `Origin`/`Host`, суворий CORS», а §16 — щоб «усі
змінюючі команди були ідемпотентні (заголовок `Idempotency-Key`)». Під час T0.7 треба було визначити те, чого ТЗ не
описує:

1. Де зберігати ключі ідемпотентності. У пам'яті процесу ключі зникають при рестарті (launchd/systemd перезапускає
   бекенд), і повтор запиту UI після рестарту виконав би дію вдруге. Таблиці для ключів у ТЗ §15 не було
   (`audit_log.idempotency_key` — лише довідкове поле журналу, без відповіді й статусу).
2. Що робити із запитом, результат якого невідомий (обробник упав, процес завершився посеред обробки).
3. Чи потрібен токен для `/system/health` і схеми OpenAPI, і чи вмикати Swagger UI.
4. Що робити, якщо `API_TOKEN` не задано, і які origins дозволяти.

## Рішення

1. **Таблиця `api_idempotency_keys`** (міграція `0002`): ключ — PK, відбиток запиту (SHA-256 методу, шляху, query,
   тіла), `owner` (екземпляр процесу), статус `IN_PROGRESS` / `COMPLETED` / `FAILED`, збережена відповідь. Запис
   `IN_PROGRESS` комітиться **до** виконання обробника (write-ahead, як `SUBMITTING` для ордерів). ТЗ §15 доповнено.
2. **`Idempotency-Key` обов'язковий** для `POST`/`PUT`/`PATCH`/`DELETE` (без нього — 400). Повтор → збережена
   відповідь; інший запит з тим самим ключем → 422; невідомий результат (`FAILED` або `IN_PROGRESS` іншого процесу)
   → 409 `IDEMPOTENCY_RESULT_UNKNOWN` і **ніколи** не виконується повторно з тим самим ключем — людина перевіряє стан і
   робить нову дію з новим ключем. Сховище недоступне до виконання → 503 без виконання. Ключі не протухають.
3. **Токен для всіх ендпоінтів**, включно з `/system/health` і `/openapi.json`. Swagger UI і ReDoc вимкнені: вони
   вантажать JavaScript з CDN в origin API (скомпрометований CDN отримав би доступ до API після введення токена).
   TS-типи для UI (T6.4) генеруються офлайн з `create_app(ctx).openapi()`.
4. **Без `API_TOKEN` торговий процес не стартує** (код виходу 15, до підключення до БД): API без токена був би
   відкритий будь-якій сторінці браузера. Токен — `SecretStr`, ≥ 32 символи token68. Порт API зайнятий → код 16.
5. **Origins — лише loopback** (`http(s)://127.0.0.1|localhost|[::1]:<порт>` без шляху), за замовчуванням
   `http://127.0.0.1:5173` (Vite); `*`, `null`, зовнішні хости відхиляє валідатор конфігу. CORS без credentials.
   `Host` — лише `127.0.0.1:<порт>` / `localhost:<порт>` (DNS rebinding). Браузерний крос-сайтовий запит без `Origin`
   (`Sec-Fetch-Site: cross-site|same-site`) — теж 403.
6. Адреса прослуховування не налаштовується (`API_BIND_HOST` = `127.0.0.1` у коді).

Розглянуті варіанти: ключі в пам'яті (відхилено — подвійне виконання після рестарту); повтор запиту з невідомим
результатом (відхилено — для дій з грошима це те саме, що повтор входу після `SUBMISSION_UNKNOWN`); health без
токена (відхилено — менше винятків у захисті; моніторинг зовні працює через dead-man's switch, T5.7, а не через опитування API).

## Наслідки

- Код: `app/api/` (`security.py`, `idempotency.py`, `audit.py`, `context.py`, `app.py`, `server.py`, `system.py`,
  `errors.py`), `app/core/config.py` (`API_PORT`, `API_TOKEN`, `API_ALLOWED_ORIGINS`), `app/__main__.py` (коди 15, 16).
- Користувач мусить додати `API_TOKEN` у `.env` до першого запуску `python -m app`.
- T6.1/T6.2: обробники отримують ключ із `request.state.idempotency_key`, пишуть `audit_log` через `AuditWriter` у тій
  самій транзакції, що й дія; ендпоінти, що збільшують експозицію, мають залежність `require_instance_lock`.
- T6.3: браузерний `WebSocket` не може задати `Authorization` — спосіб передати токен (напр. підпротокол) вирішує T6.3;
  до того WebSocket без заголовка відхиляється.
- T6.7: як UI отримує токен (введення людиною, зберігання в браузері) — вирішує T6.7; токен не повинен потрапляти в URL.
- T5.10: служба launchd/systemd має отримувати `API_TOKEN` з `.env`, а не з аргументів командного рядка.
- Ризик: таблиця ключів росте без очищення (дрібні записи, лише команди людини); за потреби — окрема задача на
  видалення **лише старих `COMPLETED`** записів (днів, не хвилин). `FAILED`, `IN_PROGRESS` і свіжі `COMPLETED` не
  видаляються: новий ключ — свідома дія людини, а повтор з тим самим ключем — автоматичний повтор UI після мережевої
  помилки, і видалений рядок дозволив би такому повтору виконати дію вдруге.

## Рев'ю T0.7 (trading-safety-reviewer) і відкриті питання

Виправлено з регресійними тестами: 500 тепер формується всередині CORS (`CatchUnhandled`) — UI бачить
`INTERNAL_ERROR`, а не «мережеву помилку»; `serve_api` не повертається, поки живі обробники запитів (інакше обробник
міг дописувати роботу після звільнення lock), а після втрати lock обробники скасовуються на початку зупинки (самим `serve_api`, не uvicorn), без graceful-очікування;
лог відмов обмежено (`RejectionLog`, підсумок — на першому запиті після вікна), відмови 401/403 закривають з'єднання;
`IN_PROGRESS`, запит якого не виконується в цьому процесі, — `IDEMPOTENCY_RESULT_UNKNOWN` (а повтор, поки переможець ще
в `begin()`, — `IN_PROGRESS`); невідомі небезпечні методи → 405;
тригер `ctb_api_idempotency_guard()` (фінальні статуси й ідентичність запиту незмінні); маскування `reason`/`target`
в аудиті; слабкий `API_TOKEN` (< 10 різних символів) відхиляється. Ліміт з'єднань uvicorn (`limit_concurrency`)
свідомо **не** задано: другий раунд рев'ю показав, що uvicorn рахує й простійні keep-alive з'єднання, тож чужа сторінка
могла б вичерпати ліміт і відрізати UI (зокрема Emergency Stop) відповіддю 503.

**Відкриті питання (рішення власника до етапу 5 / T6.2):**

1. **Збій API зупиняє весь торговий процес.** Зайнятий порт (код 16) або аварійна зупинка сервера (код 1) завершують
   процес. Поки «робота» — лише API, шкоди немає; коли в ту саму роботу під lock додадуться Protection Manager і звірка
   (T4.3, T5.x), конфлікт порту з іншим dev-сервером означатиме цикл рестартів без захисту позицій (лише біржовий SL).
   Варіанти: API як окрема задача, збій якої не зупиняє захист (процес працює «без UI» з CRITICAL-сповіщенням), або
   лишити fail-fast. Вирішити в T4.3/T5.1.
2. **Недоступне сховище ключів блокує й захисні команди.** 503 `IDEMPOTENCY_STORE_UNAVAILABLE` стосується всіх
   змінюючих запитів, зокрема Emergency Stop і закриття позиції (інваріант 6: захист не блокується). Сховище ключів —
   та сама БД: якщо вона недоступна, обробник Emergency Stop не запише й `emergency_runs`/`emergency_steps`, тож
   «виконувати захисні ендпоінти без ключа» мало що дає. Потрібен шлях захисту, незалежний і від API, і від БД
   (Telegram/CLI, дії на біржі до запису в БД). Вирішити в T4.6/T6.2.
3. **Origin `http://127.0.0.1:5173` — стандартний порт Vite.** Будь-який інший локальний Vite-проєкт на цьому порту має
   той самий origin; якщо T6.7 зберігатиме токен у `localStorage`, такий проєкт його прочитає. Вирішити в T6.7
   (нестандартний порт UI або токен лише в пам'яті сторінки).
4. **Флуд із браузера.** Наскільки реальна атака «сторінка шле тисячі запитів на 127.0.0.1», залежить від політики
   браузера (Chrome Local Network Access, Firefox, Safari) — перевірити вручну. Пом'якшено обмеженням логів і
   `Connection: close` на відмовах; ліміту з'єднань немає (він сам дозволяв відрізати UI).
