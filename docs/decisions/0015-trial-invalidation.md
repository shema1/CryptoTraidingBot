# 0015. Позначка спроби недійсною — лише людина, через `audit_log`

- **Дата:** 2026-11-02
- **Статус:** прийнято (власник проєкту обрав варіант 2026-11-02)
- **Зачеплені розділи ТЗ:** §5.2.5, §5А.9, §5А.10, §14
- **Зачеплені задачі:** T2.6, T2.12, T6.2

## Контекст

ТЗ §5.2.5 вимагає рахувати всі спроби дослідницької лінії і ніколи не скидати лічильник. Журнал
`experiment_trials` лише дописується. Повторне рев'ю `ml-leakage-auditor` T2.6 показало, що одна домінантна
спроба (наприклад, з витоком даних, ТЗ §5А.9: «PF або Sharpe вищі за 3 — майже напевно витік») ламає лінію
назавжди:

- якщо в неї ≥ 30 угод, вона роздуває розкид Sharpe між спробами, і DSR будь-якого кандидата падає до нуля
  (рев'ю: 0.998 → 0.000; поріг SR* = 1.136 на угоду);
- у PBO вона завжди найкраща і in-sample, і out-of-sample, тож PBO лінії стає беззмістовним.

Прибрати таку спробу з журналу не можна, і так має лишатися: інакше журнал перестав би бути доказом кількості
спроб.

## Рішення

Було → стало: людина може позначити спробу недійсною; позначка не видаляє спробу і не зменшує N.

- Таблиця `trial_invalidations` (міграція 0006): `trial_id` (UNIQUE — одна позначка на спробу), `reason`
  (непорожня), `confirmed_audit_id`, `created_at_ms`. Append-only (`ctb_forbid_mutation()`).
- `confirmed_audit_id` — підтверджений людиною запис `audit_log` з дією `trial.invalidate` і `target` = id спроби.
  Це перевіряє тригер `ctb_require_confirmed_audit()` (нова ціль `'trial'`), а до нього — `invalidate_trial`
  (`app/ml/validation.py`). Один запис аудиту — одна позначка (`UNIQUE (confirmed_audit_id)`).
- `open_holdout_after_gate`: позначена спроба лишається в N для DSR, але не входить у розкид Sharpe і в PBO;
  кандидатом вона не буває. Запис відкриття hold-out пише `result.invalidated_trials` (id спроби, id запису аудиту,
  причина), тож позначки видно поруч із рішенням G1.

Розглянуті варіанти:

- **Прийняти ризик** — одна спроба з витоком закривала б G1 лінії назавжди; єдиний вихід — нова лінія, а
  «лінія = торговий символ» (рішення 0004) цього не дозволяє.
- **Позначка без людини** (автоматично за порогом Sharpe) — відкидається: поріг сам став би параметром, який можна
  підібрати, а ТЗ §14 вимагає для небезпечних дій підтвердження людини.

## Наслідки

- Ризик зловживання: позначкою можна прибрати сильного суперника з PBO або з розкиду DSR. Обмеження: лише
  підтвердження людини з причиною в `audit_log`, позначка назавжди, N не зменшується, нижня межа розкиду DSR
  (`1/(T−1)`) діє далі, і кожне відкриття hold-out показує всі позначки лінії.
- API для підтвердження (`confirmed = true` в `audit_log`) — T6.2; до того запис аудиту робить людина вручну.
- Тести: `tests/db/test_guards.py` (дія, ціль, підтвердження, одна позначка, причина), `tests/db/test_constraints.py`
  (append-only), `tests/db/test_migrations.py` (крок 0006), `tests/ml/test_gate_g1.py` (спроба з витоком закриває
  G1 через DSR; після позначки — у N, але не в розкиді й PBO; кандидатом не буває; без аудиту — відмова).
