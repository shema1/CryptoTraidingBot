# 0027. Скасування біржею без запиту бота; джерело події для кожного переходу ордера

- **Дата:** 2026-11-10
- **Статус:** прийнято (2026-11-10, підтвердження власника; змінює ТЗ §7.1)
- **Зачеплені розділи ТЗ:** §7.1, §7.2
- **Зачеплені задачі:** T3.1 (і T3.3, T3.4 — застосування статусів біржі)

## Контекст

Граф ТЗ §7.1 дозволяв `CANCELED` лише після запиту бота: `OPEN/PARTIALLY_FILLED → PENDING_CANCEL → CANCELED`. Але
біржа скасовує ордери й сама, без нашого запиту. Приклади: залишок ринкового (IOC) ордера, якому забракло
ліквідності; `reduceOnly`-ордер, коли позицію вже закрито; деактивований умовний ордер. Адаптер такий статус уже
має: `ExchangeOrderStatus.CANCELED`, зокрема з `filled_qty > 0`, і `DEACTIVATED`. Ордер може бути знайдений уже
скасованим і після `SUBMISSION_UNKNOWN`. За старим графом кожне таке звичайне скасування було б помилкою
інваріанта і зупиняло б бота.

Окремо: ТЗ не казав, звідки може прийти подія кожного переходу. Тож факт біржі («виконано», «скасовано») можна
було записати з локального джерела, хоча біржа — джерело істини для фактів (AGENTS.md, інваріант 1).

## Рішення

1. **Три нові ребра, лише з подією біржі (`WS`/`REST`):** `OPEN → CANCELED`, `PARTIALLY_FILLED → CANCELED`
   (залишок скасовано, `filled_qty > 0`), `SUBMISSION_UNKNOWN → CANCELED` (ордер знайдено вже скасованим).
   Скасування на запит бота — як і раніше, через `PENDING_CANCEL`.
2. **Джерело події задане для кожного ребра** (`app/trading/order_state.py`, `TRANSITION_SOURCES`):
   - факти біржі — лише `WS`/`REST`: прийнято, виконано (частково чи повністю), скасовано, біржа відхилила
     (`SUBMITTING → REJECTED`), а також знайдено після невизначеності;
   - рішення бота — лише `LOCAL`: `CREATED → SUBMITTING` (write-ahead), `→ PENDING_CANCEL`,
     `SUBMITTING → SUBMISSION_UNKNOWN` (таймаут, обрив, 5xx);
   - `SUBMISSION_UNKNOWN → REJECTED` — будь-яке: `LOCAL` — «не знайдено після вікна перевірки», `WS`/`REST` —
     «знайдено відхиленим»;
   - `OPEN → EXPIRED` — лише факт біржі (`timeInForce`). Тайм-аут входу `entry_timeout_s` бот оформлює
     скасуванням (`OPEN → PENDING_CANCEL → CANCELED`, ТЗ §6.3).
   - Перший факт біржі про ордер (`SUBMITTING → OPEN`, `SUBMISSION_UNKNOWN → OPEN/PARTIALLY_FILLED/FILLED/CANCELED`)
     несе id ордера біржі (`exchange_order_id`) обов'язково; id приймається лише з подією біржі.

   Інше джерело — `InvariantViolation`, як і недозволений перехід. Це суворіше за старий текст ТЗ, а не м'якше.
3. **Мапінг статусу біржі** (`exchange_target`):

   | Статус біржі | Стан |
   | --- | --- |
   | `NEW`, `UNTRIGGERED`, `TRIGGERED` | `OPEN` |
   | `PARTIALLY_FILLED` | `PARTIALLY_FILLED` |
   | `FILLED` | `FILLED` |
   | `CANCELED`, `DEACTIVATED` | `CANCELED` |
   | `REJECTED` | `REJECTED` |
   | `UNKNOWN` | переходу немає, звірка — CRITICAL |

   Як застосовувати статус, що «перестрибує» стан (напр. `SUBMITTING` + `FILLED` — через `OPEN`) або вже
   застарів, вирішує обробка подій біржі (T3.3, T3.4).

## Уточнення після рев'ю `trading-safety-reviewer` (2026-11-10, підтверджене власником)

- `OPEN → EXPIRED` спершу дозволяв і `LOCAL`. Адаптер не має статусу біржі EXPIRED, тож ребро було б лише
  локальним: бот оголосив би живий на біржі ордер термінальним без підтвердження. Ордер вибув би з активних
  (`ix_orders_bot_id_active`), і на наступному сигналі новий вхід дав би подвійну позицію поза RiskGate. Тепер —
  лише факт біржі, а тайм-аут входу — скасування.
- `SUBMISSION_UNKNOWN → REJECTED` спершу дозволяв лише `LOCAL`. Ордер, знайдений REST-перевіркою відхиленим, не
  розв'язувався б, а нові ордери бота, і виходи теж, стояли б до ескалації. Тепер — і з подією біржі.
