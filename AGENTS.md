# AGENTS.md — Crypto Trading Bot & ML Analytics

Спільні інструкції для всіх AI-агентів (Claude Code, Cursor). Повне ТЗ — `AppInfo.md` (далі «ТЗ §N»).
План робіт і задачі — `docs/ai/TASKS.md`. Перш ніж починати задачу, знайди її там і прочитай вказані розділи ТЗ.

## Що це

Локальний бот для Bybit USDT-perpetual (API v5) з ML-сигналами, жорстким Risk Engine і безпечною поведінкою при збоях.
Помилка в коді = втрата реальних грошей. **Коректність і безпека важливіші за швидкість, лаконічність і «красу».**

## Стек

- Backend `apps/backend`: Python 3.11+, FastAPI, SQLAlchemy 2 + Alembic, asyncpg, CCXT (async/Pro), pydantic v2, structlog.
- ML: pandas, numpy, LightGBM (основна модель, CPU), scikit-learn, Optuna. XGBoost і PyTorch/GPU відкладено (ТЗ §5.6). Підхід — meta-labeling (ТЗ §5.1).
- Frontend `apps/web`: React + Vite + TypeScript, Lightweight Charts. TS-типи API генеруються з OpenAPI.
- БД: PostgreSQL + TimescaleDB (Docker Compose). Черги — таблиця `jobs`, блокування — advisory lock.
- Якість: pytest, ruff, mypy (strict для `exchange/ trading/ risk/ protection/ reconcile/`), pre-commit.

## Команди

```bash
docker compose up -d timescaledb                 # БД
cd apps/backend && uv sync                       # залежності
uv run alembic upgrade head                      # міграції (лише локальна dev-БД)
uv run pytest -q                                 # усі тести
uv run pytest -q -m "not testnet and not slow"   # швидкі тести
uv run ruff check . && uv run ruff format --check . && uv run mypy app
cd apps/web && npm ci && npm run gen:api && npm run typecheck && npm test
```

Якщо команда ще не існує (етап 0) — створи її в межах задачі, а не обходь.

## Незмінні інваріанти (порушення = блокер)

1. **Джерела істини:** біржа — для фактів (позиції, ордери, fills, баланс); БД — для намірів (сигнали, рішення, конфіг, журнал).
2. **Час:** скрізь UTC, `int` мілісекунди. Секунди, naive `datetime`, `time.time()` для торгової логіки — заборонені.
3. **Гроші та кількості:** `Decimal` (або цілі в мінімальних одиницях). `float` для ціни/кількості/PnL в торговому шарі заборонений. Округлення: кількість — вниз до `qtyStep`, ціни — до `tickSize`; ризик рахується за округленими значеннями.
4. **Вся торгівля — лише через `ExchangeAdapter`.** Paper / Testnet / Live виконують один і той самий код. Прямі виклики CCXT поза `app/exchange/` заборонені. Bybit `category` інкапсульований в адаптері.
5. **RiskGate має veto.** Жоден ордер, що збільшує експозицію, не відправляється поза `RiskGate`. `reduceOnly`-виходи та аварійне закриття RiskGate не блокує ніколи.
6. **Fail-closed:** будь-яка невизначеність (помилка інференсу, прогалина в даних, розсинхрон часу > 1 с, stale signal, невдала звірка, `SUBMISSION_UNKNOWN`, `ENTRY_FILLED_UNPROTECTED`) блокує **нові входи**, але ніколи не блокує захист і закриття.
7. **Ордери:** машина станів — граф із ТЗ §7.1; недозволений перехід = помилка інваріанта. Write-ahead: запис `SUBMITTING` з `clientOrderId` комітиться **до** мережевого виклику. `clientOrderId = "tb" + uuid4().hex`. Повтор — лише з тим самим `clientOrderId`.
8. **Fills** дедуплікуються за `exec_id`; середня ціна, комісії, PnL рахуються лише з `fills`.
9. **Захист позиції:** позиція без підтвердженого біржового SL існує не довше `protection_timeout_s`; інакше — примусове закриття. SL можна рухати лише в бік зменшення ризику.
10. **ML без look-ahead і без самообману:** фічі для свічки `t` — лише з даних, відомих на закриття `t-1` (свічки, закриті старші ТФ, дані деривативів). Один `compute_features()` для навчання та live; один симулятор угоди `ml/trade_sim.py`; ліміти й розмір — ті самі функції, що в live. Інтерполяція OHLCV заборонена. Кожна спроба записується в журнал (DSR/PBO). Hold-out не відкривається поза Gate G1.
11. **Ідемпотентність:** повторна обробка тієї самої свічки/події не створює дублів (UNIQUE-обмеження в БД, а не лише перевірки в коді).
12. **Секрети** ніколи не потрапляють у логи, API-відповіді, тести, фікстури, коміти. Ключі без права виводу.
13. **Сервіси слухають лише `127.0.0.1`.**
14. **Послаблення лімітів ризику, запуск Live, вихід з `EMERGENCY_STOP`** — лише через явне підтвердження людини + `audit_log`. Агент ніколи не змінює значення за замовчуванням у бік більшого ризику.
15. **Код і документація завжди відповідають одне одному.** Будь-яка зміна коду (поведінка, параметр, default, статус, таблиця, API, команда, змінна оточення) оновлює документацію в тій самій задачі, і навпаки. Якщо код розходиться з ТЗ (`AppInfo.md`) — не виправляй мовчки ні те, ні інше: запитай користувача, а зміну ТЗ фіксуй у `docs/decisions/`. Деталі — `.claude/rules/documentation.md`.

## Як працювати агенту

- Перед зміною коду в `exchange/ trading/ risk/ protection/ reconcile/ ml/` — **спочатку план**, потім тести, потім код (TDD). Тести мають покривати і «щасливий шлях», і збої (таймаут, 5xx, обрив WS, дубль події, частковий fill).
- Не вигадуй поведінку Bybit API. Якщо не впевнений у полі/коді помилки — перевір документацію (MCP context7) або залиш явний `TODO(verify-bybit)` + тест на Testnet, а не припущення.
- Не змінюй вже застосовані міграції Alembic — лише нова міграція.
- Не вимикай, не пропускай (`skip`, `xfail`) і не послаблюй існуючі тести, щоб «зробити зелено». Якщо тест неправильний — поясни чому і запитай.
- Не додавай нові залежності без пояснення; версії закріплюються в lock-файлі.
- Не запускай нічого проти **mainnet** і не використовуй live-ключі. Мережеві тести — лише Testnet (`-m testnet`).
- Після завершення задачі: запусти тести/лінтери, **онови документацію, яку зачепила зміна** (ТЗ — лише з підтвердженням), онови статус задачі в `docs/ai/TASKS.md`, коротко опиши, що змінено, які документи оновлено і які ризики лишились.
- Для задач з ризиком R3 після реалізації — незалежне рев'ю (субагент `trading-safety-reviewer` / skill `safety-check`).

## Стиль коду

- Python: повні type hints, `from __future__ import annotations`, pydantic v2 моделі на межах, `structlog` з контекстом (`bot_id`, `symbol`, `client_order_id`, `signal_id`). Без `print`. Без голих `except:`; `except Exception` — лише з логуванням і переведенням у безпечний стан.
- async скрізь у торговому процесі; блокуючі виклики (ML-навчання, pandas на великих даних) — у воркері або `run_in_executor`.
- Ніяких глобальних змінних стану; стан — у БД або в явно переданих об'єктах.
- Назви, статуси й коди причин — як у ТЗ (`ENTRY_FILLED_UNPROTECTED`, `RISK_DAILY_LOSS`, …). Коментарі та документація — українською, ідентифікатори — англійською.
