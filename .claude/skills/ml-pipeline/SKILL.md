# ML-пайплайн без витоку даних

Вимоги: ТЗ §5, §5А (v3.1), `docs/decisions/0001-ml-methodology.md`. Детальні правила — `.claude/rules/ml-pipeline.md`.

## Перед зміною фіч
1. Для кожної фічі: формула, вікно, джерело (1h / 4h / 1d / деривативи), з яких даних рахується. Переконайся, що використовується лише відоме на закриття `t-1`.
2. Старші ТF: береться остання **повністю закрита** 4h/1d свічка до `t-1` включно. Дані деривативів: `merge_asof(direction="backward")` за часом публікації, а не за часом періоду.
3. Заборонені конструкції: `shift(-n)`, `center=True`, `bfill`, глобальні `mean/std`, `fit` скейлера до розбивки, `resample` без перевірки закритості бару, funding/OI з майбутнім таймстемпом.
4. Онови `feature_schema_hash` (автоматично) і `preprocessing_version` (вручну, semver).

## Перед зміною розмітки або бектесту
1. Уся логіка закриття угоди — лише в `ml/trade_sim.py`; витрати — лише з `risk/costs.py`; ліміти — лише з `risk/limits.py`; розмір — `calc_position_size()`.
2. Перевір: `open[t]`, ATR(`t-1`), бар'єри з самої `t`, SL першим, геп через SL → `open`, time-stop → `open[t+horizon_bars]`, taker на виходах, окремий `slippage_sl`.

## Обов'язкові тести (додай/онови)
- **Look-ahead:** змінити дані після `t-1` (свічки 1h, поточну незакриту 4h/1d, дані деривативів) → фічі для `t` не змінились.
- **Parity:** буфер == офлайн (останні N рядків, допуск `1e-9`).
- **Shuffled labels:** на перемішаних мітках результат ≈ 0.
- **Симулятор:** синтетичні свічки на кожне правило (TP+SL в одній свічці, геп, time-stop); LONG/SHORT взаємовиключні за тих самих свічок і `tp_atr_mult ≥ sl_atr_mult`; обидва TP інакше → `FLAT` + `both_reached_tp` (рішення 0013).
- **Ваги унікальності:** відомі перекриття → очікувані ваги.
- **Розбивка:** embargo ≥ `horizon_bars`; purging за часом для всіх символів; hold-out не потрапляє в жоден фолд/Optuna/калібрування/вибір порогів.
- **Статистика:** DSR/PBO на синтетиці з відомим результатом; блочний bootstrap.
- **Правило EV:** граничні значення.

## Множинне тестування
- Кожна спроба (Optuna, нова фіча, новий таргет, новий варіант правила) → `experiment_trials`. Не видаляй і не «перезапускай з нуля» журнал, щоб покращити DSR.

## Інтерпретація
Якщо результат «занадто хороший» (PF/Sharpe > 3, accuracy > 80%) або DSR низький при гарному Sharpe — спочатку шукай витік або підгонку, повідом користувача, не позначай модель як успішну. ML-фільтр, що не кращий за правило без фільтра, — не успіх.
Після зміни — субагент `ml-leakage-auditor`.
