## 1. Мета, межі та не-цілі

**Мета.** Алгоритмічна торгівля криптодеривативами з ML-сигналами, із жорстким Risk Engine та безпечною поведінкою при збоях.

**Не-цілі:** мультикористувацький режим, висока доступність (HA), HFT, одночасна робота з кількома біржами на старті, комерційна експлуатація.

**Реальні ризики локального запуску** (і чим закриваються):

| Ризик | Захист |
| --- | --- |
| ПК вимкнувся / зник інтернет при відкритій позиції | Обов'язковий серверний SL на біржі. Dead-man's switch (розділ 12) |
| Рестарт ОС або падіння процесу | Обов'язкова звірка при старті до відновлення ботів (розділ 11) |
| Той самий акаунт запущено з двох комп'ютерів | Призначений хост для кожного акаунта, ідентифікатор хоста в `clientOrderId`, чужі ордери/позиції при звірці → `PAUSED` + CRITICAL (розділи 6.4, 11.4) |
| Помилка в коді або моделі | Ліміти Risk Engine, Testnet, мінімальний розмір на старті |
| Витік ключів | Ключі без права виводу (перевіряється при старті), IP whitelist, окремий субакаунт з обмеженим балансом, `.env` з доступом лише власника |

## 2. Технологічний стек

- **Бекенд (`apps/backend`)**: Python 3.11+, FastAPI, SQLAlchemy 2 + Alembic, asyncpg, CCXT (async) та/або CCXT Pro для WebSocket, pydantic v2, structlog.
- **ML**: pandas, numpy, LightGBM (основна модель), scikit-learn (калібрування), Optuna. XGBoost і PyTorch (CUDA) — відкладено (розділ 5.6).
- **Фронтенд (`apps/web`)**: React, Vite, TypeScript, Lightweight Charts, нативний WebSocket.
- **Інфраструктура**: Docker Compose: лише TimescaleDB. Бекенд і фронт запускаються локально.
- **Сповіщення**: Telegram Bot API.
- **Якість**: pytest, ruff, mypy, pre-commit. Типи API генеруються з OpenAPI-схеми FastAPI у TypeScript (замість ручних shared-types).

## 4. Дані та час

### 4.1. Зберігання свічок (TimescaleDB)

- Hypertable `candles(exchange, symbol, timeframe, open_time_ms, open, high, low, close, volume, is_closed)`, первинний ключ `(exchange, symbol, timeframe, open_time_ms)`.
- Зберігаються **лише закриті свічки**. Незакрита свічка в БД не потрапляє.
- Інкрементальне докачування: при старті та за розкладом; повторне завантаження ідемпотентне (`ON CONFLICT DO NOTHING`).
- **Compression** — після 7 днів. **Retention Policy — не застосовується** (свічки компактні, а історія потрібна для перенавчання).
- Додатково зберігаються funding rate history та, за потреби, mark price.

### 4.2. Політика пропусків

- Інтерполяція OHLCV **заборонена**.
- Кожна прогалина записується в таблицю `data_gaps(symbol, timeframe, from_ms, to_ms, detected_at)` і логується.
- **Навчання:** вікна фіч, що перетинають прогалину, виключаються з вибірки.
- **Live:** якщо прогалина потрапляє у вікно фіч поточного сигналу, бот не торгує на цій свічці, шле попередження і запускає докачування.

### 4.3. Час

- Скрізь **UTC, мілісекунди (int)**, включно з API і прикладами JSON. Секунди заборонені.
- При старті та кожні 10 хв: порівняння локального часу з `fetch_time()` біржі. Розбіжність більше 1 с означає **блок нових входів** і попередження (рекомендується системна синхронізація NTP). Для приватних запитів використовується налаштований `recvWindow`.

**Годинник після сну або стрибка часу.** Сон і гібернація вимкнені (розділи 12.1, 12.1.1), але на випадок збою бекенд щосекунди порівнює монотонний і системний годинники. При стрибку понад 1 с бот переходить у `RECONCILING` (розділ 6.1), чекає завершення синхронізації годинника ОС і повертається в `RUNNING` лише тоді, коли розбіжність з часом біржі менша за 1 с і звірка пройшла успішно. Запит із застарілим `timestamp` біржа відхиляє, тому найгірший наслідок — пропущена свічка.

### 4.4. Кілька символів і дані деривативів

- **Символи для навчання:** фіксований список `research_symbols` (5–8 ліквідних USDT-perpetual, обраних за ліквідністю на початок історії, розділ 5А.6). Свічки 1h завантажуються для всіх; торгує бот лише своїм символом.
- **Дані деривативів з історією** (backfill через REST Bybit v5, інкрементально й ідемпотентно): open interest; premium index, mark- і index-свічки; long/short ratio; funding (розділ 4.1). Глибина історії кожного ендпоінта перевіряється на початку відповідної задачі й фіксується в документації.
- **Ліквідації — лише вперед:** заднім числом їх не завантажити, тому колектор публічного WebSocket працює з етапу 1 і агрегує їх по годинах (кількість і обсяг окремо для long і short) у `liquidations_hourly`. Періоди, коли колектор не працював, записуються в `data_gaps`.
- Колектор — окремий легкий процес `python -m app.data.collector`: без торгових ключів, з автозапуском разом із бекендом, REST-запити — через власний rate limiter у межах виділеної частки ліміту (розділ 6.5).
- Усі ці дані зберігаються в UTC мс, у фічах використовуються за правилом «значення, відоме станом на закриття `t-1`» і підпадають під політику пропусків розділу 4.2.

## 5. ML-пайплайн

> Ревізія методології v3.1 — див. `docs/decisions/0001-ml-methodology.md`.

### 5.1. Постановка задачі

Задача розв'язується у два кроки (ітерації), обидва використовують один симулятор угоди (розділ 5.2.1):

1. **Ітерація 1 — meta-labeling (основний шлях).**
   - **Первинна стратегія** (`primary_strategy`) — просте правило (1–2 варіанти з бейзлайнів розділу 5А.3, наприклад пробій або перетин EMA, з мінімумом параметрів). На закритті свічки `t-1` вона видає кандидата у вхід з напрямком (LONG або SHORT) по `open[t]`. Параметри правила фіксуються **до** навчання ML лише на walk-forward і не підбираються разом із моделлю.
   - **Meta-модель** — бінарний класифікатор (LightGBM), який для кожного кандидата оцінює ймовірність `p`, що угода досягне TP. Мітка: `1` — симульована угода закрилась по TP; `0` — по SL або time-stop.
   - ML лише **фільтрує** сигнали правила. Вхід без сигналу правила неможливий.
   - **Варіант без ML (`rule_only`).** Якщо ML-фільтр не додає цінності (розділ 5А.11), первинна стратегія може торгувати сама — але лише як окремий артефакт моделі з `label_type: "rule_only"`, що проходить ті самі критерії допуску (розділ 5.3, крім умови 4) і має власний коридор результатів. Сигнал правила без затвердженого артефакту (ML-моделі або `rule_only`) не торгується ніколи.
2. **Ітерація 2 — пряме прогнозування (порівняльний варіант).** Для кожної свічки `t` окремо симулюються LONG-угода (TP = +`tp_atr_mult`·ATR, SL = −`sl_atr_mult`·ATR) і SHORT-угода (дзеркально). Класи:
   - `LONG` — LONG-угода досягла TP;
   - `SHORT` — SHORT-угода досягла TP;
   - `FLAT` — обидві закрились по SL або time-stop.

   `LONG` і `SHORT` одночасно неможливі (доводиться тестом). Для першої перевірки конвеєра дозволено спрощення `LONG` проти `FLAT`.

Спільні правила:

- **Фічі** обчислюються **лише з даних, відомих на момент закриття свічки `t-1`** (свічки, старші таймфрейми, дані деривативів). Один модуль `features.py` використовується і в навчанні, і в live (єдине джерело істини).
- **Рішення про вхід** приймає правило очікуваної вигоди (розділ 5.5.1), а не «гола» впевненість. Розмір позиції визначає Risk Engine, а не ймовірність.
- Клас «не торгувати» обов'язковий: бот має право не входити.

### 5.2. Симуляція угоди, витрати, бектест і валідація

#### 5.2.1. Єдиний симулятор угоди

Модуль `ml/trade_sim.py` — **єдине** місце, де визначено, як закривається угода. Його використовують розмітка таргета, бектест і розрахунок очікуваної вигоди.

- **Опорна ціна** бар'єрів — `open[t]` (як у live, розділ 6.6). ATR — на момент `t-1`. Множники — з `target_params`.
- Бар'єри перевіряються починаючи з самої свічки `t` (її high/low). **SL перевіряється за mark-свічками** (`mark_index_candles`), бо на біржі SL спрацьовує за `MarkPrice` (розділ 9.1); TP — за звичайними свічками (`LastPrice`). Якщо mark-свічок для періоду немає — SL за звичайними свічками, і це позначається в журналі експерименту.
- **Неоднозначність OHLC:** якщо в одній свічці досягнуто і TP, і SL, угода вважається **збитковою (SL першим)**.
- **Геп через SL:** якщо свічка **відкрилась** уже за рівнем SL, вихід — за `open` цієї свічки (гірше за SL). Геп через TP: вихід за ціною TP (вигідніший геп не враховується — песимістично).
- **Time-stop:** якщо за `horizon_bars` свічок жоден бар'єр не досягнуто, вихід за `open[t + horizon_bars]` (market, як у live).
- До ціни входу і цін виходу застосовується модель витрат (розділ 5.2.2).

#### 5.2.2. Модель витрат

Модуль `risk/costs.py`, спільний для симулятора, бектесту і `calc_position_size()`:

| Складова | Правило |
| --- | --- |
| Комісія входу | taker (вхід market) або maker (post-only) |
| Комісія виходів | taker на SL, TP і time-stop (захист на Bybit у режимі `Full` виконується market — перевіряється на Testnet, розділ 19) |
| Slippage входу `slippage_entry` | фіксована частина (bps) + частка ATR; зсуває ціну входу проти угоди |
| Slippage SL `slippage_sl` | окремий параметр, за замовчуванням **2× slippage входу**; плюс правило гепу (5.2.1) |
| Slippage TP `slippage_tp` | окремий параметр |
| Funding | нараховується, якщо позиція відкрита на момент виплати funding |
| Затримка входу | моделюється для перевірки `max_signal_age_ms` |

SL/TP лишаються прив'язаними до опорної ціни; slippage змінює фактичні ціни виконання. Параметри slippage **калібруються** за фактичними fills Demo/Testnet (різниця між ціною тригера та ціною виконання) і не лишаються фіксованими назавжди. Систематичне перевищення над моделлю дає попередження (розділ 5.5).

#### 5.2.3. Бектест

- Використовує той самий симулятор (5.2.1), ту саму модель витрат (5.2.2), ту саму функцію розміру `calc_position_size()` і **ті самі чисті функції лімітів** `risk/limits.py`, що й `RiskGate`: одна позиція одночасно, cooldown після серії збитків, денний ліміт збитку, `max_trades_per_day`, зупинка при просадці, time-stop. Бектест торгує рівно так, як торгуватиме бот.
- Кожна відмова фіксується з кодом причини (`RISK_COOLDOWN` тощо), як `decision_log` у live.
- Обов'язковий стрес-прогін: подвоєні комісії та slippage.
- Бектест без витрат не є прийнятним доказом якості.

#### 5.2.4. Валідація

- **Walk-forward** з purged time-series CV та **embargo ≥ `horizon_bars`**.
- **Кілька символів** (розділ 4.4): purging і embargo виконуються **за часом для всіх символів одночасно** — рядок будь-якого символу з часом, що перетинає тестовий відрізок, вилучається з train.
- **Мінімум угод на фолд:** якщо в тестовому відрізку торгового символу менше `min_trades_per_fold` угод (за замовчуванням 20), відрізок автоматично подовжується (3 → 6 місяців), кількість фолдів зменшується.
- **Ваги унікальності:** мітки з перекриттям вікон (для `horizon_bars = 24` сусідні мітки дивляться в одне майбутнє) отримують вагу `w = середнє за час життя мітки (1 / кількість одночасно активних міток)`. Рахується всередині кожного символу; множиться на ваги класів; передається в модель як `sample_weight`.
- **Final hold-out** (останні 15–20% історії) не використовується в Optuna, калібруванні, виборі `min_edge` і параметрів первинної стратегії; відкривається лише за правилами Gate G1 (розділ 5А.10).
- **Метрика Optuna:** медіана out-of-sample результату по фолдах **після витрат** мінус штраф за розкид, з мінімальною кількістю угод; не accuracy.

#### 5.2.5. Множинне тестування та статистика

- **Облік спроб.** Журнал `experiments` / `experiment_trials` рахує **всі** спроби дослідницької лінії: кожну спробу Optuna і кожну ітерацію фіч, таргета, первинної стратегії, таймфрейму. Для кожної спроби зберігається ряд її out-of-sample результатів. **Дослідницька лінія** = торговий символ; лічильник спроб **ніколи не скидається** — ні при зсуві hold-out, ні при зміні підходу (meta, пряме прогнозування, `rule_only`), ні при перенавчанні.
- **Deflated Sharpe Ratio (DSR)** рахується для кожного експерименту з урахуванням загальної кількості спроб. Поріг для Gate G1: `DSR ≥ 0.95` (налаштовується).
- **PBO** (probability of backtest overfitting, метод CSCV, 16 блоків) рахується один раз перед Gate G1 зі збережених результатів спроб. Поріг: `PBO < 0.5`.
- **Довірчий інтервал PF** — **блочний bootstrap** (блоки по тижню), а не bootstrap окремих угод: угоди залежні через ринкові режими.
- **Коридор очікуваних результатів** для live (розділ 5.7) будується тим самим блочним bootstrap з out-of-sample угод.

### 5.3. Критерії допуску моделі до live

Hold-out перевіряє **рецепт** моделі (фічі + таргет + первинна стратегія + параметри + правило входу), а не конкретний файл моделі (розділ 5.4.1). Пороги конфігуруються. Умови 1–4 дають рецепту статус придатного; модель, навчена за ним, отримує CANDIDATE (дозволені Demo і Testnet); умова 5 переводить модель у APPROVED (дозволений Live):

1. Gate G1 пройдено (розділ 5А.10), включно з `DSR ≥ 0.95` і `PBO < 0.5`.
2. Hold-out: net profit factor ≥ 1.2; сумарно по out-of-sample (walk-forward + hold-out) ≥ 100 угод торгового символу, з них ≥ 30 на самому hold-out (інакше hold-out розширюється); нижня межа 90% **блочного** bootstrap-інтервалу PF вища за 1.0.
3. Макс. просадка hold-out (бектест з лімітами live, 5.2.3) не перевищує ліміт Risk Engine; результат стабільний на ≥ 70% walk-forward фолдів (кожен фолд ≥ `min_trades_per_fold`).
4. Для meta-labeling: стратегія **з ML-фільтром** перевершує первинну стратегію **без фільтра** за net-результатом на тих самих out-of-sample відрізках. Інакше ML не додає цінності і не використовується. Для `rule_only` ця умова не застосовується.
5. Успішний прогін на Testnet не менше 7 днів без аномалій і ручне підтвердження в UI. **Цей прогін перевіряє механіку** (ордери, SL, звірка, реконекти), **а не прибутковість**: за 7 днів на 1h набирається 5–15 угод, що статистично нічого не доводить про перевагу моделі. Прибутковість у реальному часі контролює коридор розділу 5.7.

**Статуси моделі:** `TRAINED` → `CANDIDATE` → `APPROVED` → `RETIRED`. Live приймає лише `APPROVED`; це перевіряється і при старті бота, і в `RiskGate`. Модель, навчена з незакоміченими змінами коду (`git_dirty = true`), не може стати `CANDIDATE` — лише для експериментів.

4. Регулярне перенавчання (раз на 1–3 місяці, розділ 5А.10) працює так само.

**Підхоплення нової моделі.** У бота є `model_version` і `pending_model_version`. Перемикання відбувається лише коли відкритої позиції немає, на межі свічки і лише на модель потрібного статусу (для Live — `APPROVED`). Відкат на попередню версію — одна дія.

**Процедура перемикання моделі:** (1) бот переходить у `PAUSED` з причиною `MODEL_SWAP`; (2) скасовуються власні вхідні ордери бота (limit/post-only); (3) через REST перевіряється, що відкритих ордерів немає і розмір позиції дорівнює 0; (4) `model_version` змінюється на `pending_model_version`, перевіряються `feature_schema_hash`, версії бібліотек і статус моделі; (5) бот повертається в `RUNNING`. Якщо будь-яка умова не виконана, перемикання відкладається до наступної межі свічки, а стара модель лишається чинною.

### 5.5. Інференс у live (in-process)

Інференс виконується викликом функції в тому ж процесі (HTTP між сервісами не потрібен). Результат зберігається в `signals`:

```json
{
  "signal_id": "uuid",
  "bot_id": "uuid",
  "entry_candle_open_time_ms": 1718000000000,
  "features_candle_open_time_ms": 1717996400000,
  "feature_schema_hash": "sha256:...",
  "model_version": "lgbm-meta-2026-11-15-001",
  "primary_signal": "LONG",
  "prediction": "LONG",
  "probability": 0.47,
  "expected_edge_atr": 0.14,
  "decision": "ENTER",
  "computed_at_ms": 1718000001420
}
```

`entry_candle_open_time_ms` — свічка `t`, на відкритті якої виконується вхід; `features_candle_open_time_ms` — свічка `t-1`, з якої розраховані фічі; `computed_at_ms` — час розрахунку сигналу. `primary_signal` — сигнал первинної стратегії (`NONE`, якщо його немає; тоді інференс не виконується і запис не створюється). `decision` — `ENTER` або `SKIP` з причиною в `decision_log`.

- `UNIQUE (bot_id, entry_candle_open_time_ms)` гарантує не більше одного сигналу на свічку.
- **Stale signal:** якщо `computed_at_ms − entry_candle_open_time_ms > max_signal_age_ms` (за замовчуванням 5000), вхід **не виконується**. Реалістично: свічка надходить із затримкою, плюс розрахунок фіч, тож «перші мілісекунди» — не вимога, а цільова межа.
- **Fail-closed:** якщо інференс упав, перевищив таймаут, схема або версія бібліотеки не збігаються, є прогалина в даних (свічки або дані деривативів, що входять у фічі), нові входи блокуються. Сигнал первинної стратегії **без** ML-фільтра не торгується (виняток — затверджений артефакт `rule_only`, розділ 5.1). **Відкрита позиція при цьому не залишається без нагляду:** вона живе під біржовим SL/TP, а за наявності `max_hold_bars` закривається за time-stop.

#### 5.5.1. Правило входу за очікуваною вигодою

```text
TP_net = tp_atr_mult · ATR − витрати_TP     (комісії + slippage входу і TP, у цінових одиницях)
SL_net = sl_atr_mult · ATR + витрати_SL     (комісії + slippage входу і SL)
EV     = p · TP_net − (1 − p) · SL_net
```

- `p` — **калібрована** ймовірність досягнення TP (розділ 5А.8). Вихід за time-stop консервативно вважається повним SL.
- Вхід, лише якщо `EV ≥ min_edge` (за замовчуванням 0.10 ATR) **і** `p ≥ min_confidence` (додаткова нижня межа-запобіжник).
- `min_edge` і `min_confidence` обираються **лише на walk-forward**, не на hold-out, і фіксуються в `model_metadata.decision_rule`.
- При малому ATR витрати займають більшу частку руху, тож бот автоматично торгує рідше.
- `p` і `EV` зберігаються в `signals` і `decision_log`.

**Швидкість розрахунку фіч у live:**

- Для кожного бота в пам'яті тримається кільцевий буфер закритих свічок і даних деривативів. Довжина = найбільше вікно фіч з урахуванням старших таймфреймів (для EMA(50) на 1d — щонайменше 50 днів, тобто ≥ 1300 годинних свічок) + запас. Після закриття свічки `t-1` фічі обчислюються **лише для останнього рядка** на основі буфера, а не перераховуються на всій історії.
- Використовується **той самий код** `compute_features()`, що й при навчанні. Parity-тест (розділ 18.1) перевіряє, що інкрементальний live-розрахунок дає ті самі значення, що й офлайн-розрахунок на всій історії.
- Модель завантажується й «прогрівається» при старті бота, а не на першому сигналі. Закриття свічки визначається за WS-подією про закриту свічку, REST-запит — резервний канал.
- Для кожного сигналу вимірюється й зберігається затримка від відкриття свічки `t` до `computed_at_ms`. Ціль — менше 1 с, жорстка межа — `max_signal_age_ms`.
- Якщо вхід виконується із запізненням, ринок міг відійти від `open[t]`. Це покривають `max_slippage_bps` та модель витрат (розділ 5.2.2). Реальний slippage входу та виходів (у частках ATR) зберігається в `decision_log`; систематичне перевищення над моделлю витрат дає попередження й вимагає перекалібрування моделі витрат.

**Порядок обробки закритої свічки:**

1. Подія закриття від WebSocket оновлює кільцевий буфер у пам'яті.
2. Первинна стратегія перевіряє, чи є кандидат у вхід. Якщо немає — далі лише запис свічки.
3. Якщо є — негайно виконуються розрахунок фіч, інференс і правило входу (5.5.1).
4. Паралельно закрита свічка записується в TimescaleDB ідемпотентно (`ON CONFLICT DO NOTHING`); запис не блокує інференс.
5. При рестарті буфер відновлюється з БД і догружається пропущеними свічками за період простою (розділ 11.1).

### 5.6. Optuna та задачі

- Підбір гіперпараметрів виконується як задача в таблиці `jobs` (статуси `QUEUED/RUNNING/DONE/FAILED/CANCELED`) окремим воркер-процесом. Закриття браузера задачу не перериває; прогрес транслюється через WebSocket.
- Кожна спроба записується в `experiment_trials` з рядом out-of-sample результатів (для DSR і PBO, розділ 5.2.5).
- Тренування не повинно конкурувати з live-циклом за ресурси: воркер має знижений пріоритет.

* **Обчислення — CPU.** LightGBM на обсягах проєкту (до сотень тисяч рядків) навчається за секунди; вузьке місце — розрахунок фіч і walk-forward, які виконуються на CPU. Результати CPU також краще відтворюються.
* **GPU відкладено.** Перемикач `device: cpu | cuda` лишається в конфігу, за замовчуванням `cpu`. Задачі з налаштування GPU (RTX 5070 / Blackwell: потрібні збірки XGBoost і PyTorch із CUDA 12.8+, перевірка у WSL2) винесені в розділ «Відкладені» плану робіт. **Умова повернення:** один прогін Optuna триває понад 1 годину або в проєкті з'являється нейромережа.

### 5.7. Моніторинг моделі: drift і коридор результатів

- **Журнал рішень:** кожен сигнал первинної стратегії, `p`, `EV`, хеш фіч, ризик-рішення та результат угоди зберігаються для розбору.
- **Drift фіч:** PSI ключових фіч проти навчальної вибірки, щодня. PSI > 0.25 → попередження; PSI > 0.25 у 3 перевірках поспіль → бот `PAUSED` зі сповіщенням.
- **Коридор очікуваних результатів (правило зупинки).** При отриманні моделлю статусу `CANDIDATE` (до прогонів у Demo/Testnet) з out-of-sample угод її рецепта блочним bootstrap рахується коридор: для кожної кількості угод `N` — 5-й перцентиль сумарного результату в `R` (одиницях ризику на угоду) та максимальна серія збитків. Коридор записується в `model_metadata.live_corridor` і **не змінюється без нового затвердження моделі**.
- Після кожної закритої угоди в **Demo і Live** (на Testnet ціни нереалістичні, тож там коридор лише записується в лог і не зупиняє бота): якщо сумарний результат нижчий за коридор **або** серія збитків перевищує 1.5× максимуму з бектесту, бот переходить у `PAUSED` з причиною `MODEL_UNDERPERFORMS`, надсилається сповіщення в Telegram; відновлення **лише вручну**.
- На перших угодах коридор широкий (немає хибних зупинок) і з часом звужується. Рішення «зупинитися» ухвалене заздалегідь, а не під час просадки.

## 5А. Практичний посібник з навчання моделі

Мета навчання — не знайти «найточнішу» модель, а перевірити, чи є на історії перевага, яка переживає комісії, новий період часу та поправку на кількість спроб. Якщо такої переваги немає, це нормальний результат, а не помилка проєкту.

### 5А.1. Словник

| Термін | Простими словами |
| --- | --- |
| Плече (leverage) | множник позиції відносно власних коштів: при 3× позиція втричі більша за заставу |
| Маржа | застава, що тримає позицію |
| Ліквідація | примусове закриття позиції біржею, коли збиток з'їв маржу |
| Funding rate | періодична виплата між лонгами та шортами (зазвичай раз на 8 годин): додаткова витрата або дохід |
| Open interest (OI) | сумарний обсяг відкритих позицій на ринку |
| Premium index | наскільки ціна перпетуалу відрізняється від спотового індексу |
| Taker / maker | taker забирає ліквідність (комісія вища), maker виставляє лімітний ордер (комісія нижча) |
| Slippage | різниця між очікуваною та фактичною ціною виконання |
| ATR | середній розмах свічки; міра волатильності |
| R | одиниця ризику: збиток угоди при спрацюванні SL. Результат +2R — прибуток удвічі більший за ризик |
| Drawdown (просадка) | падіння капіталу від попереднього піку |
| Profit factor (PF) | сума прибутків ÷ сума збитків; 1.0 — нуль, менше 1 — збиток |
| Look-ahead bias | випадкове використання інформації з майбутнього |
| Overfitting (перенавчання) | модель запам'ятала історію замість закономірності |
| Hold-out | ділянка історії, яку не чіпають до фінальної перевірки |
| Walk-forward | навчання на минулому, перевірка на наступному відрізку, далі вікно зсувається вперед |
| Embargo / purging | проміжок між навчальними та тестовими даними, щоб мітки не перетиналися |
| Baseline | проста еталонна стратегія, з якою порівнюється модель |
| Первинна стратегія | просте правило, що пропонує вхід і напрямок; ML лише вирішує, брати сигнал чи ні |
| Meta-labeling | навчання моделі на питанні «чи виграє ця конкретна угода первинної стратегії» |
| Ваги унікальності | менша вага для рядків, мітки яких перекриваються в часі, щоб модель не рахувала один результат 24 рази |
| Множинне тестування | чим більше спроб, тим вищий шанс випадково знайти «гарний» результат |
| DSR (Deflated Sharpe Ratio) | Sharpe, скоригований на кількість спроб: чи результат кращий за найкращий випадковий |
| PBO | імовірність, що «найкраща» конфігурація насправді випадкова (перевіряється на різних шматках історії) |
| Блочний bootstrap | оцінка розкиду результату перестановкою цілих тижнів, а не окремих угод |
| Очікувана вигода (EV) | середній чистий результат угоди з урахуванням імовірності й витрат |
| Survivorship bias | помилка, коли для навчання беруть лише активи, що «вижили» до сьогодні |

### 5А.2. Реалістичні очікування

- **Витрати значні.** Стандартна комісія Bybit для taker приблизно 0,055% за сторону, тобто близько 0,11% за вхід і вихід, плюс slippage, найбільший — на стопах (актуальні тарифи перевірте на біржі). Якщо типовий рух ціни за час угоди менший за \~0,5%, витрати з'їдають більшу частину переваги.
- **Тому старт — таймфрейм 1h** (за потреби 4h): менше угод, більший рух на угоду, менший вплив комісій. 15m не рекомендується для першої моделі.
- **Висока точність не потрібна і не очікується.** При TP/SL = 2:1 беззбитковість настає приблизно при 36–40% угод, що досягають TP (з урахуванням витрат); 40–50% — вже добрий результат. Accuracy 80–90% майже завжди означає витік даних.
- **Більшість перших моделей не проходять hold-out.** Це очікувано. Розділ 5А.11 описує, що робити тоді.
- **Testnet — перевірка механіки, а не прибутковості.** Тиждень на 1h — це 5–15 угод; висновки про перевагу з них робити не можна.

### 5А.3. Покроковий процес

1. **Дані:** 3–5 років на 1h для фіксованого списку з 5–8 ліквідних символів (розділ 4.4) + дані деривативів, наскільки дозволяє історія API. Колектор ліквідацій працює з етапу 1. Прогалини зафіксовані (розділ 4.2).
2. **Бейзлайни:** результат «завжди FLAT» (нуль), «завжди LONG», випадкових входів із тими самими витратами та простих правил (перетин EMA, пробій). З них обираються 1–2 **первинні стратегії**; їхні параметри фіксуються на walk-forward.
3. **Фічі:** стартовий набір з розділу 5А.4, один модуль для навчання й live.
4. **Таргет:** meta-мітки для кандидатів первинної стратегії (розділ 5.1), параметри — розділ 5А.5. Ваги унікальності (розділ 5.2.4).
5. **Розбивка:** hold-out виділяється одразу й відкладається (розділ 5А.6).
6. **Перше навчання — LightGBM зі стандартними параметрами**, бінарна meta-модель, ваги класів × ваги унікальності, без Optuna.
7. **Оцінка:** лише out-of-sample результати walk-forward, після витрат, з лімітами live; метрики розділу 5А.9; порівняння з первинною стратегією без фільтра.
8. **Optuna** — лише коли пункти 6–7 дали хоч якийсь сигнал, у вузьких діапазонах (розділ 5А.7). Кожна спроба записується.
9. **Калібрування** ймовірності та вибір `min_edge` на walk-forward (розділ 5А.8).
10. **Gate G1** (DSR, PBO, внутрішні критерії) → **hold-out один раз** (розділ 5А.10).
11. **Перенавчання рецепта на всіх даних** (розділ 5.4.1), розрахунок коридору (5.7) → CANDIDATE.
12. **Demo → Testnet** (розділ 13) → ручне затвердження → `APPROVED`.
13. **Ітерація 2** (пряме 3-класове прогнозування) — лише після завершення ітерації 1 або якщо вона не пройшла; її спроби рахуються в тому ж журналі.

### 5А.4. Стартовий набір фіч (≈25)

Усі фічі обчислюються лише з даних, відомих на момент закриття свічки `t-1`, і виражаються у **відносних** величинах (відсотки, відношення), а не в абсолютних цінах. Сирі рівні цін моделі не передаються. Ідентифікатор символу на старті як фіча не передається.

| Група | Приклади |
| --- | --- |
| Дохідності | log-return за 1, 3, 6, 12, 24 свічки |
| Волатильність | ATR ÷ ціна, стандартне відхилення дохідностей (12, 24), (high − low) ÷ close |
| Тренд і моментум | RSI(14), відстань ціни до EMA(20) та EMA(50), нахил EMA(20) |
| Старші таймфрейми | 4h і 1d, побудовані з 1h: дохідність останніх закритих 4h/1d свічок, ATR ÷ ціна на 4h і 1d, відстань до EMA(50) на 1d, нахил тренду 1d. Береться лише остання **повністю закрита** старша свічка до `t-1` включно |
| Обсяг | обсяг ÷ середній обсяг за 24 свічки |
| Форма свічки | тіло ÷ діапазон, верхня та нижня тінь ÷ діапазон |
| Деривативи | funding rate; зміна OI за 1/6/24 свічки; premium index; long/short ratio; ліквідації за годину ÷ середнє (лише коли історія покриває весь навчальний діапазон) |
| Контекст первинної стратегії | сила сигналу правила (наприклад, відстань між EMA ÷ ATR) — для meta-labeling |
| Час | година доби та день тижня (кодування sin/cos) |

Правила: не більше 30 фіч; сильно корельовані фічі прибрати; фіча з джерела деривативів додається, лише коли її історія покриває весь навчальний діапазон (інакше прогалини за розділом 4.2); дані деривативів вирівнюються за правилом «значення, відоме станом на `t-1`». Після першого навчання переглянути важливість фіч: якщо головна фіча виглядає підозріло (наприклад, лише година доби), шукати витік.

### 5А.5. Таргет: стартові значення

- Таймфрейм 1h, `tp_atr_mult = 2.0`, `sl_atr_mult = 1.0`, `horizon_bars = 24`. ATR береться на момент `t-1`.
- **Ітерація 1 (meta):** мітка `1/0` для кожного кандидата первинної стратегії (розділ 5.1). Кандидати однієї стратегії перекриваються менше, ніж мітки кожної свічки, але ваги унікальності все одно обов'язкові.
- **Ітерація 2 (пряма):** дві симуляції (LONG і SHORT) на кожну свічку, класи `LONG/SHORT/FLAT` (розділ 5.1). `FLAT` зазвичай переважає (60–80%), тож використовуються ваги класів.
- Метрика — не accuracy, а результат торгівлі після витрат.
- **Перекриття міток:** мітки сусідніх свічок дивляться в одне майбутнє, тож їх не можна випадково перемішувати між train і test (embargo/purging ≥ `horizon_bars`, розділ 5.2.4) і в навчанні вони отримують ваги унікальності.
- Параметри таргета на етапі Optuna не перебираються.

### 5А.6. Розбивка даних

- **Символи:** фіксований список 5–8 ліквідних USDT-perpetual (наприклад BTC, ETH, SOL, XRP, BNB, DOGE, ADA, LTC). Список обирається **за ліквідністю на початок історії** і фіксується в конфігу (`research_symbols`), щоб уникнути survivorship bias. Торговий символ на старті — BTC.
- **Hold-out:** останні 15–20% історії (за часом, для всіх символів). До фінальної перевірки його не відкривають.
- **Walk-forward на решті:** вікно навчання, що розширюється; тестовий відрізок ≈ 3 місяці (з подовженням до 6, якщо угод торгового символу менше `min_trades_per_fold`); між train і test — embargo; purging за часом для всіх символів одночасно.
- **Метрики окремо:** по всіх символах і лише по торговому символу. **Рішення про допуск приймається за торговим символом.**
- **Режими ринку:** результат дивиться окремо по фолдах і роках. Модель, що працює лише в одному періоді, не вважається надійною.

### 5А.7. Optuna: бюджет і діапазони

| Параметр LightGBM | Діапазон |
| --- | --- |
| `num_leaves` | 8–64 |
| `max_depth` | 3–8 |
| `learning_rate` | 0.01–0.1 (логарифмічно) |
| `n_estimators` | 200–1500 з early stopping |
| `min_child_samples` | 50–500 |
| `subsample`, `colsample_bytree` | 0.6–1.0 |
| `reg_lambda` | 0–10 |

- **100–200 спроб — достатньо.** Чим більше спроб, тим вищий шанс випадково знайти «гарний» результат; кожна спроба знижує DSR (розділ 5.2.5).
- Метрика — медіана результату по фолдах мінус штраф за розкид, а не найкращий фолд.
- Параметри таргета і первинної стратегії на цьому етапі **не перебираються** разом із параметрами моделі.
- Якщо Optuna покращила результат лише трохи порівняно зі стандартними параметрами, лишається простіша модель.

### 5А.8. Калібрування та правило входу

Ймовірності, що повертає бустинг, не є реальними ймовірностями. Модель калібрується (isotonic або Platt) на out-of-sample даних, і перевіряється діаграмою надійності: коли модель каже 0.45, чи справді приблизно 45% таких угод досягають TP. Від якості калібрування напряму залежить правило входу за очікуваною вигодою (розділ 5.5.1). `min_edge` і `min_confidence` обираються за walk-forward, **не за hold-out**.

### 5А.9. Як читати результати

| Ознака | Що це зазвичай означає |
| --- | --- |
| Net PF або Sharpe вищі за 3 на hold-out | майже напевно витік даних або помилка в бектесті |
| Навчання блискуче, out-of-sample близько нуля | перенавчання |
| Результат тримається на 1–2 фолдах із 6–8 | везіння, а не закономірність |
| Менше \~100 угод | висновки статистично слабкі |
| Результат руйнується при подвоєнні комісії та slippage | перевага надто тонка |
| Accuracy понад 80% | витік даних або дисбаланс класів |
| Модель майже завжди каже «не входити» | поріг `min_edge` надто суворий або сигналу немає |
| DSR < 0.95 при гарному Sharpe | результат пояснюється кількістю спроб, а не перевагою |
| PBO ≥ 0.5 | вибір «найкращої» конфігурації нестабільний — перенавчання на етапі вибору |
| ML-фільтр не кращий за первинну стратегію без фільтра | ML не додає цінності; або змінити підхід, або торгувати правилом (5А.11) |
| Добре на всіх символах, погано на торговому | перевага не переноситься на BTC; допуск не надається |

**Обов'язкові перевірки на витік:** (1) тест із розділу 18.1: зміна майбутніх даних (свічок, старших таймфреймів, даних деривативів) не змінює фічі; (2) перемішування міток: на перемішаних мітках результат має впасти до нуля. Якщо ні, у конвеєрі є помилка.

### 5А.10. Життєвий цикл моделі

- **Перенавчання:** за розкладом раз на 1–3 місяці або при спрацюванні drift (розділ 5.7), за процедурою розділу 5.4.1. Частіше не варто.
- **Нова модель** проходить той самий конвеєр (розділ 5.3), потім щонайменше 2 тижні працює в Demo паралельно з діючою. Заміна відбувається лише вручну і тільки якщо кандидат не гірший за діючу на тому самому відрізку.
- Усі версії зберігаються; відкат на попередню — одна дія.
- **Hold-out «спалюється» після перегляду.** Кожне налаштування після його перегляду — це вже підгонка. Для нової оцінки потрібен новий, ще не бачений відрізок історії.

**Політика hold-out і внутрішні критерії (Gate G1):**

- **Крок 1 — ітерації лише на walk-forward.** Усі експерименти (фічі, таргет, первинна стратегія, Optuna) оцінюються на walk-forward validation. Hold-out при цьому не відкривається. Кожна спроба записується в `experiment_trials`.
- **Gate G1:** hold-out дозволено відкрити, лише коли модель пройшла внутрішні критерії на walk-forward: медіана net profit factor по фолдах ≥ 1.15; ≥ 70% фолдів у плюсі; кожен фолд ≥ `min_trades_per_fold` угод; ≥ 100 угод торгового символу сумарно; результат не руйнується при подвоєнні комісії та slippage; **`DSR ≥ 0.95`**; **`PBO < 0.5`**; для meta-labeling — ML-фільтр кращий за первинну стратегію без фільтра.
- **Крок 2 — hold-out відкривається лише після G1**, і кожне відкриття записується в журнал експериментів (дата, модель, результат). Дозволено **не більше двох відкриттів** на один hold-out.
- **Після невдалої перевірки** модель не підганяється під hold-out. Якщо відкриття вичерпано, hold-out **зсувається вперед**: беруться новіші дані, що з'явилися за час розробки, а старий hold-out стає частиною walk-forward.
- **Demo/Testnet — перевірка механіки**; прибутковість у реальному часі контролює коридор (розділ 5.7).
- **Журнал експериментів** (`experiments`, `experiment_trials`): seed, діапазон даних, символи, первинна стратегія, параметри, метрики, OOS-результати кожної спроби, загальна кількість спроб лінії, DSR, PBO, прапорець «відкрито hold-out».

### 5А.11. Критерій зупинки

Якщо після 2–3 розумних ітерацій модель не проходить розділ 5.3, торгувати нею не можна. Порядок дій:

1. Ітерація 1 — meta-labeling з 1–2 первинними стратегіями.
2. Ітерація 2 — пряме прогнозування (розділ 5.1).
3. Змінити торговий символ або таймфрейм (4h).
4. Якщо й це не дало результату — торгувати **первинною стратегією без ML** як артефактом `rule_only` (розділ 5.1): Demo/Testnet, а після проходження критеріїв розділу 5.3 (крім умови 4) — Live з мінімальним розміром, поки модель дозріває.

Усі спроби з пунктів 1–3 рахуються в одному журналі й знижують DSR наступних моделей. Бот — це інфраструктура (ордери, ризики, захист), а ML-модель — замінний компонент. Тому все, що описано в розділах 6–12, можна повністю відпрацювати на Testnet із простою стратегією, поки модель дозріває.

## 6. Торговий рушій (Live Trading Engine)

### 6.1. Статуси бота

`STOPPED` → `STARTING` (обов'язкова звірка зі станом біржі) → `RUNNING` ⇄ `PAUSED`; із будь-якого стану → `ERROR` або `EMERGENCY_STOP`.

| Статус | Нові входи | Виходи / керування SL | Вихід зі статусу |
| --- | --- | --- | --- |
| `STARTING` | ні | так (після звірки) | автоматично після успішної звірки |
| `RUNNING` | так | так | — |
| `PAUSED` | ні | так | вручну або за правилом (напр., новий день) |
| `ERROR` | ні | так | вручну після аналізу |
| `EMERGENCY_STOP` | ні | лише закриття | лише вручну |

**Причини `PAUSED` і вихід із паузи.** Кожна пауза має код причини (`pause_reason`) у `bots` і журналі. Бот виходить з паузи лише тоді, коли знято **всі** активні причини.

| Причина (`pause_reason`) | Звідки | Вихід |
| --- | --- | --- |
| `DAILY_LOSS` | денний ліміт (8.5) | автоматично о 00:00 UTC |
| `COOLDOWN` | серія збитків (8.5) | автоматично після `cooldown_bars` |
| `DATA_GAP` | прогалина у вікні фіч (4.2) | автоматично після докачування й перевірки |
| `INSTRUMENT_NOT_TRADING` | статус інструмента (15) | автоматично, коли інструмент знову торгується |
| `MODEL_SWAP` | перемикання моделі (5.4.1) | автоматично після завершення процедури |
| `DRIFT` | PSI (5.7) | лише вручну |
| `MODEL_UNDERPERFORMS` | коридор результатів (5.7) | лише вручну |
| `UNKNOWN_POSITION`, `FOREIGN_HOST_ORDERS` | звірка (11.4) | лише вручну, після рішення людини |
| `LEVERAGE_MISMATCH` | звірка (11.4) | автоматично після успішного виправлення, інакше вручну |
| `MANUAL` | користувач | вручну |

**`RECONCILING`** — тимчасовий стан: бот входить у нього при втраті зв'язку з приватним WebSocket, після `SUBMISSION_UNKNOWN` або при стрибку системного годинника (розділ 4.3). Нові входи заборонені; керування SL і закриття позицій дозволені. Вихід — автоматично в попередній статус після успішної звірки (розділ 11.2).

### 6.2. Ізоляція позицій

- **Один бот на символ на акаунт:** часткове `UNIQUE`-обмеження в БД на `(account_id, symbol)` для ботів зі статусами, відмінними від `STOPPED`. Режим позицій біржі — one-way, тож два боти на одному символі неминуче конфліктували б.
- Позиції, відкриті поза ботом (вручну), **не «усиновлюються»** (див. розділ 11).

### 6.3. Цикл бота на закритті свічки

1. Отримано закриту свічку `t-1` (WebSocket або REST-перевірка). Перевірка цілісності вікна фіч (немає прогалин).
2. Первинна стратегія: чи є кандидат у вхід і в який бік. Якщо ні — цикл завершується.
3. Інференс meta-моделі → запис `signals` (унікальність `bot_id + entry_candle_open_time_ms`).
4. Перевірка stale signal та fail-closed умов (розділ 5.5).
5. Рішення про дію за правилом очікуваної вигоди (розділ 5.5.1): відкрити позицію або нічого (при відкритій позиції сигнал лише логується).
6. **Risk Engine** розраховує розмір і дозволяє або відхиляє дію (розділ 8). Рішення і причина логуються.
7. Створення ордера в машині станів (розділ 7) і відправка через `ExchangeAdapter`.
8. Після `FILLED` або `PARTIALLY_FILLED` — Position Protection Manager (розділ 9).

Кожен крок ідемпотентний: повторна обробка тієї самої свічки (після рестарту) не створює дублів завдяки `UNIQUE`-обмеженням на сигнали та `clientOrderId`.

**Відновлення після падіння між сигналом і ордером.** Первинними для ордерів є таблиця `orders` і машина станів (розділ 7); таблиця `signals` — історія намірів. Сигнал має статус `NEW` → `EXECUTING` → `DONE` або `EXPIRED_UNEXECUTED`, а вхідний ордер має `UNIQUE(signal_id)`. Після рестарту для кожного сигналу в `NEW`/`EXECUTING`: (1) ордер існує — обробка продовжується за його станом; (2) ордера немає — він створюється лише якщо сигнал ще не stale і всі ризик-перевірки проходять, інакше сигнал стає `EXPIRED_UNEXECUTED`; (3) ордер у `REJECTED`/`EXPIRED` (у тому числі після `SUBMISSION_UNKNOWN`, розділ 7.2) — повторна спроба для цього сигналу не виконується, сигнал стає `EXPIRED_UNEXECUTED`, причина фіксується в `decision_log`. Новий сигнал на ту саму свічку не створюється (`UNIQUE(bot_id, entry_candle_open_time_ms)`).

### 6.4. Конкурентність (один процес)

- `asyncio.Lock` на кожного бота: цикл одного бота не виконується паралельно.
- PostgreSQL advisory lock на рівні додатка: запобігає випадковому запуску **другого екземпляра** бекенду (другий процес завершується при старті).
- Optimistic concurrency: у `bots` є поле `version`. Кожна команда оновлює стан через `UPDATE ... WHERE version = :v`; при конфлікті операція повторюється з актуальним станом.

**Процеси.** Три процеси з одного репозиторію:
- **торговий** (FastAPI, цикли ботів, WebSocket) — єдиний працює з ордерами; тримає single-instance advisory lock;
- **воркер** `python -m app.jobs.worker` (Optuna, навчання, backfill) — не торгує, не має торгових ключів, взаємодіє з торговим процесом лише через таблицю `jobs` та файли моделей; на одній БД працює лише один воркер (власний single-instance lock), бо частка rate limit (розділ 6.5) розрахована на один процес;
- **колектор** `python -m app.data.collector` (дані деривативів, ліквідації, розділ 4.4) — не торгує, не має торгових ключів.

**Один акаунт біржі — один комп'ютер.** Проєкт може працювати на Windows + WSL2 і на macOS, але кожен комп'ютер має власну БД, тож advisory lock не бачить інший комп'ютер. Правила:
- кожен комп'ютер має `HOST_ID` (2 символи `[a-z0-9]`, задається в `.env`, унікальний для кожного комп'ютера);
- для кожного акаунта (`exchange_accounts`) у конфігу вказано `allowed_host_id`; бот на іншому комп'ютері для цього акаунта **не стартує**;
- `HOST_ID` входить у `clientOrderId` (розділ 7.2), тож звірка розпізнає ордери, створені іншим комп'ютером (розділ 11.4);
- рекомендовано: Live — лише на комп'ютері, що працює 24/7; Demo/Testnet для розробки — на будь-якому, але з різними акаунтами або з перенесенням `allowed_host_id` вручну.

**Запуск воркера.** Воркер — окремий процес із того самого репозиторію (`python -m app.jobs.worker`), без додаткових фреймворків на кшталт Celery. Воркер у циклі бере задачі з `jobs` запитом `SELECT … FOR UPDATE SKIP LOCKED`, виконує їх по одній (GPU-задачі не паралеляться), оновлює прогрес і `heartbeat_at` у `jobs` та не торгує. Окремий процес обрано свідомо: навчання й Optuna навантажують CPU та GPU й не повинні конкурувати з торговим циклом; воркер працює зі зниженим пріоритетом ОС. Задача, що лишилась у `RUNNING` після аварії воркера, при наступному старті за `heartbeat_at` переводиться в `FAILED` і може бути перезапущена вручну.

**Надійність advisory lock** (`docs/decisions/0006-instance-lock.md`). Блокування береться на окремому з'єднанні (поза пулом) з **серверними** TCP keepalive сесії (`tcp_keepalives_idle`, `tcp_keepalives_interval`, `tcp_keepalives_count`), щоб PostgreSQL швидко виявляв «мертву» сесію після аварійного завершення процесу і звільняв lock; `application_name` сесії містить pid процесу ОС. При старті процес повторює спроби взяти lock протягом `lock_wait_s` (за замовчуванням 60 с), зокрема поки БД ще недоступна; якщо не вдалося, він завершується й показує, яка сесія тримає блокування (`pg_locks` + `pg_stat_activity`). Під час роботи процес перевіряє, що lock досі його (сигнал закриття з'єднання + heartbeat із таймаутом); якщо lock втрачено (рестарт БД, обрив, перехоплення) — CRITICAL і завершення процесу, а новий старт іде через звірку (розділ 11.1). Примусове перехоплення (`--force-takeover`) виконується лише вручну з інтерактивного терміналу (без TTY — відмова), після підтвердження, що старий процес не працює: процес показує власника, вимагає ввести `TAKEOVER`, пише `audit_log` і лише тоді завершує сесію-власника.

### 6.5. Централізований Rate Limiter

Усі REST-виклики проходять через один модуль:

- черга процесу з token bucket окремо для кожної групи ендпоінтів із вагами;
- використання лімітів, що повертає біржа (заголовки Bybit про залишок ліміту), для динамічної корекції;
- при `429` або кодах перевищення — експоненційний backoff з jitter і тимчасова пауза всієї черги;
- **пріоритети:** захисні та аварійні запити (SL, закриття) > звірка > запити даних. Завантаження історії ніколи не блокує захисні виклики.
- **Кілька процесів:** ліміт Bybit для публічних запитів рахується на IP і спільний для всіх процесів. Кожен процес має власний limiter із фіксованою часткою загального ліміту (за замовчуванням торговий 50%, воркер 30%, колектор 20%), тож backfill і колектор фізично не можуть вичерпати ліміт торгового процесу. При `429` у будь-якому процесі — backoff саме цього процесу.

### 6.6. Типи входу та виходи

- **Вхід:** за замовчуванням market із перевіркою `max_slippage_bps` (орієнтир — остання ціна на момент відправки; при перевищенні вхід скасовується). Post-only limit-вхід у версії 1 **вимкнено**: бектест моделює лише market-вхід по `open[t]` і не моделює ймовірність виконання лімітного ордера. Вмикати post-only можна лише після того, як симулятор (розділ 5.2.1) отримає модель виконання limit-ордерів і модель пройде валідацію з нею.
- **Виходи:** біржовий SL/TP; `max_hold_bars` (time-stop); примусове закриття Risk Engine.
- Усі виходи — `reduceOnly`.

**Параметри виходів беруться з моделі.** SL і TP при вході: `entry − sl_atr_mult × ATR(t-1)` та `entry + tp_atr_mult × ATR(t-1)` (для SHORT навпаки); ATR фіксується на момент входу. Множники беруться з `model_metadata.target_params`, а не з налаштувань бота, тож змінити їх окремо від моделі не можна. Time-stop: `max_hold_bars = horizon_bars` (бот може лише скоротити це значення, але не збільшити); після цього позиція закривається `reduceOnly` market. Поки позиція відкрита, нові сигнали лише логуються: розвороту й доливання у версії 1 немає. Ціни SL/TP рахуються від ціни на момент відправки, а `max_slippage_bps` обмежує розбіжність із фактичним входом.

**Time-stop і збої відправки.** Закриття за time-stop проходить через ту саму машину станів (розділ 7), включно з `SUBMISSION_UNKNOWN`. Інваріант для звірки: якщо вік позиції перевищив `horizon_bars`, а позиція на біржі ще є, закриття `reduceOnly` market повторюється (з новим `clientOrderId`, якщо попередній ордер став `REJECTED` або `EXPIRED`). Весь цей час позиція захищена біржовим SL, тож додаткове переставлення ордерів не потрібне.

## 7. Машина станів ордера та ідемпотентність

### 7.1. Стани та переходи

Машина станів — це **граф**, а не лінійний ланцюг. Дозволені лише переходи з таблиці; будь-який інший відхиляється та логується як помилка інваріанта.

| З | В | Подія |
| --- | --- | --- |
| `CREATED` | `SUBMITTING` | запис у БД перед мережевим викликом (write-ahead) |
| `SUBMITTING` | `OPEN` | біржа підтвердила прийняття |
| `SUBMITTING` | `REJECTED` | біржа відхилила (код помилки зберігається) |
| `SUBMITTING` | `SUBMISSION_UNKNOWN` | таймаут, обрив з'єднання, 5xx |
| `SUBMISSION_UNKNOWN` | `OPEN` / `PARTIALLY_FILLED` / `FILLED` | ордер знайдено на біржі за `clientOrderId` |
| `SUBMISSION_UNKNOWN` | `REJECTED` | ордера немає на біржі після підтвердженого вікна перевірки |
| `OPEN` | `PARTIALLY_FILLED` | частковий fill |
| `OPEN` / `PARTIALLY_FILLED` | `FILLED` | повне виконання |
| `OPEN` / `PARTIALLY_FILLED` | `PENDING_CANCEL` | відправлено скасування |
| `PENDING_CANCEL` | `CANCELED` | біржа підтвердила скасування |
| `PENDING_CANCEL` | `FILLED` / `PARTIALLY_FILLED` | ордер встиг виконатися до скасування |
| `OPEN` | `EXPIRED` | вичерпано `timeInForce` або `entry_timeout_s` |

Термінальні стани: `FILLED`, `CANCELED`, `REJECTED`, `EXPIRED`. З термінального стану переходів немає: повторна спроба — це **новий** ордер (новий запис і новий `clientOrderId`), і лише для виходів (розділ 7.2). Часткове виконання з наступним скасуванням залишку фіксується як `CANCELED` з `filled_qty > 0`.

### 7.2. Правила ідемпотентності

- **`clientOrderId`:** `tb` + `HOST_ID` (2 символи, розділ 6.4) + UUID4 у hex **без дефісів** — разом 36 символів, максимум для Bybit `orderLinkId` (довжина перевіряється в T3.7). Префікс `tb` позначає ордери бота, `HOST_ID` — комп'ютер, що їх створив.
- **Write-ahead:** запис ордера в стані `SUBMITTING` із `clientOrderId` комітиться в БД **до** відправки на біржу. Після падіння процесу в БД завжди видно, що відправка могла відбутися.
- **`SUBMISSION_UNKNOWN` — алгоритм розв'язання:**
  1. нові ордери для цього бота **не відправляються**;
  2. запит `fetch_order_by_client_id` (REST) і перевірка приватного WS-потоку;
  3. до 3 перевірок з інтервалом 2–3 с; додатково звіряється позиція/баланс;
  4. знайдено — перехід у відповідний стан; не знайдено після всіх перевірок — `REJECTED` (ордера не існує);
  5. **повтор після `REJECTED`:**
     - **вхідний ордер не повторюється ніколи** — за час перевірок (до ~9 с) сигнал гарантовано перевищив `max_signal_age_ms`, тож сигнал стає `EXPIRED_UNEXECUTED` (розділ 6.3);
     - **вихід (`reduceOnly`: time-stop, закриття Risk Engine, Emergency Stop, примусове закриття без SL)** повторюється **новим** ордером із новим `clientOrderId`, якщо позиція на біржі ще відкрита. Подвійного закриття не буде: `reduceOnly` не може зменшити позицію нижче нуля;
  6. якщо біржа недоступна довше `unknown_escalation_s` (за замовчуванням 60) — бот `ERROR`, критичне сповіщення в Telegram.
- **Fills:** окрема таблиця `fills(exec_id UNIQUE, order_id, price, qty, fee, fee_currency, ts_ms)`. Дедуплікація за `exec_id` (ті самі події приходять і з WS, і з REST). Середня ціна входу, комісії та PnL рахуються **лише з `fills`**.
- **Append-only журнал** `order_events` фіксує кожен перехід (стан, причина, джерело події: WS/REST/локально).

## 8. Risk Engine

### 8.1. Принципи

- **Veto-право:** жоден ордер на збільшення експозиції не може бути відправлений поза `RiskGate`. ML-модель та UI не мають способу його обійти.
- **Виходи (`reduceOnly`) та аварійне закриття** Risk Engine не блокує ніколи.
- Діє однаково в Demo, Testnet та Live.
- **Окремо для кожного акаунта** (`exchange_accounts`): `risk_config`, equity, денний ліміт, просадка, лічильники угод і статус Risk Engine (`NORMAL/RESTRICTED/HALTED`) ведуться для кожного акаунта окремо. Збиток чи `HALTED` у Demo ніяк не впливає на Live, і навпаки.
- Конфігурація ризиків версіонується; **послаблення** лімітів застосовується лише після явного підтвердження в UI та запису в журнал.
- Кожна відмова логується з кодом причини (`RISK_DAILY_LOSS`, `RISK_MAX_POSITIONS` тощо).

### 8.2. Параметри (значення за замовчуванням — консервативні)

| Параметр | За замовч. | Призначення |
| --- | --- | --- |
| `risk_per_trade_pct` | 0.5% | максимальний ризик на угоду від equity (при спрацюванні SL) |
| `max_leverage` | 3× | верхня межа ефективного плеча |
| `max_open_positions` | 3 | загальна кількість позицій |
| `max_total_exposure_pct` | 150% | сумарний номінал від equity |
| `max_notional_per_symbol_usd` | задається | абсолютна межа на символ |
| `daily_loss_limit_pct` | 2% | денний збиток (реалізований + нереалізований, від equity на 00:00 UTC) |
| `max_drawdown_pct` | 10% | просадка від піку equity |
| `max_consecutive_losses` | 4 | серія збиткових угод |
| `cooldown_bars` | 8 | пауза після серії збитків |
| `max_trades_per_day` | 10 | захист від «розкрутки» |
| `min_liq_distance_sl_multiple` | 2.0 | ціна ліквідації не ближче ніж 2× відстані до SL |
| `max_slippage_bps` | 15 | відхилення ціни входу |
| `min_equity_usd` | задається | нижче — вхід заборонено |
| `max_funding_rate_abs` | опція | не входити проти надмірного funding |

### 8.3. Розрахунок розміру позиції

```text
risk_usd   = equity * risk_per_trade_pct
sl_dist    = |entry_price - sl_price|  (+ запас на slippage і комісію)
qty_risk   = risk_usd / sl_dist
qty_lev    = equity * max_leverage / entry_price
qty_expo   = (equity * max_total_exposure_pct - current_notional) / entry_price
qty        = floor_to_lot( min(qty_risk, qty_lev, qty_expo, qty_symbol_cap) )
```

Якщо `qty` менший за мінімальний лот або мінімальний номінал біржі, входу немає (ризик не підвищується заради мінімального лота). Перед відправкою обчислюється розрахункова ціна ліквідації; при порушенні `min_liq_distance_sl_multiple` розмір зменшується або вхід відхиляється. Плече на біржі виставляється явно (`set_leverage`) і перевіряється при звірці.

Розрахунок виконує **єдина функція** `calc_position_size()` (`risk/sizing.py`): її викликають і `RiskGate`, і бектестер. Модель витрат також спільна. Parity-тест (розділ 18.1) перевіряє, що однакові вхідні дані дають однаковий розмір позиції в бектесті та в live-коді. Так само спільні **чисті функції лімітів** `risk/limits.py` (одна позиція, cooldown, денний збиток, `max_trades_per_day`, просадка, time-stop): без БД і мережі, `RiskGate` і бектестер викликають їх однаково (розділ 5.2.3), parity-тест покриває і їх. Запас `sl_dist` на slippage береться з параметра `slippage_sl` моделі витрат (розділ 5.2.2).

**Equity для розрахунку розміру.** Базою для `risk_usd` є `sizing_equity = min(wallet_balance, total_equity)`. Так нереалізований прибуток відкритих позицій **не збільшує** розмір наступних угод до закриття, а нереалізований збиток **зменшує** його (чисте використання wallet balance ігнорувало б плаваючий збиток). Для денного ліміту збитків і просадки (розділи 8.2, 15) використовується `total_equity` з урахуванням нереалізованого PnL, щоб плаваючі збитки спрацьовували в лімітах одразу. Значення беруться з біржі (`fetch_balance`) при кожному розрахунку, а не з локальної пам'яті.

**Округлення за правилами інструмента.** Кількість округлюється вниз до `qtyStep` і не може бути меншою за `minOrderQty` та мінімальний номінал. Ціни входу, SL, TP і limit-ордерів округлюються до `tickSize`, а ризик розраховується вже за округленими значеннями. Правила беруться з кешу `instruments` (розділ 15): оновлення при старті, кожні 24 години та після відхилення ордера через фільтри біржі. Якщо після округлення кількість стає нульовою, вхід пропускається, ризик не збільшується.

### 8.4. Pre-trade перевірки (усі мають пройти)

1. Статус бота `RUNNING`, статус Risk Engine акаунта не `HALTED`, бот запущено на дозволеному для акаунта комп'ютері (`allowed_host_id`).
2. Сигнал не stale, дані без прогалин, час синхронізований, схема фіч і версії бібліотек збігаються, модель має потрібний статус (для Live — `APPROVED`).
3. Захист попередньої позиції підтверджений (немає стану `ENTRY_FILLED_UNPROTECTED`).
4. Не перевищено жоден ліміт із 8.2.
5. Немає незавершених ордерів у `SUBMISSION_UNKNOWN`.
6. Остання успішна звірка зі станом біржі не старіша за `max_reconcile_age_s`.

### 8.5. Дії при перевищенні лімітів

| Подія | Дія |
| --- | --- |
| Денний збиток ≥ ліміту | усі боти **цього акаунта** `PAUSED` (`DAILY_LOSS`) до 00:00 UTC, відкриті позиції лишаються під SL (опція: примусове закриття); Telegram |
| Просадка ≥ `max_drawdown_pct` | `HALTED` **для цього акаунта**: автоматично запускається протокол Emergency Stop для акаунта (розділ 10), відновлення лише вручну |
| Серія збитків | пауза `cooldown_bars` для бота |
| Помилка звірки / невідома позиція | символ у `PAUSED`, критичне сповіщення |
| Drift (`DRIFT`) або дані з пропусками (`DATA_GAP`) | бот `PAUSED`; вихід — за таблицею розділу 6.1 |
| Результат нижче коридору (`MODEL_UNDERPERFORMS`) | бот `PAUSED`, Telegram, вихід лише вручну (розділ 5.7) |

Статуси Risk Engine (окремо для кожного акаунта): `NORMAL`, `RESTRICTED` (боти на паузі) і `HALTED`. Перехід у `HALTED` автоматично запускає протокол Emergency Stop для цього акаунта; вихід лише вручну.

## 9. Position Protection Manager (SL/TP)

### 9.1. Модель захисту

- **Основний варіант — нативні TP/SL біржі на рівні позиції** (Bybit: `takeProfit`/`stopLoss` у запиті на створення ордера або `trading-stop` на позиції, режим `tpslMode=Full`). Такий захист прив'язаний до *позиції*, а не до конкретного ордера: він не потребує існування позиції на момент відправки, автоматично масштабується під фактичний розмір (часткові fills) і знімається при закритті позиції. Це усуває проблему `reduceOnly`-стопів, які біржа відхиляє, поки позиції ще немає.
- **Запасний варіант:** якщо нативний режим недоступний, захист встановлюється **після першого fill** через `set_position_protection`.
- **Тригер SL:** `MarkPrice` (стійкіший до проколів ціни на тонкому ринку); тригер TP — `LastPrice`. Тип виконання SL — market. Параметри `sl_trigger_by`, `tp_trigger_by` налаштовуються.
- Режими: one-way, isolated margin. Лише ці комбінації підтримуються адаптером; інші відхиляються на старті.

### 9.2. Стан `ENTRY_FILLED_UNPROTECTED`

Після першого fill позиція має отримати підтверджений SL протягом `protection_timeout_s` (за замовчуванням 5 с). Підтвердження — позиція на біржі містить ненульовий `stopLoss` (REST або WS).

1. Невдача → до 3 повторів із backoff.
2. Невдача після повторів → **примусове закриття** позиції (`reduceOnly` market) і критичне сповіщення; бот переходить у `ERROR`.
3. Поки стан `ENTRY_FILLED_UNPROTECTED` активний, нові входи заборонені (перевірка 3 у розділі 8.4).

**Інваріант:** позиція без підтвердженого біржового SL існує не довше `protection_timeout_s`.

### 9.3. Часткові заповнення

- Нативний захист у режимі `Full` масштабується біржею. Менеджер **додатково перевіряє** відповідність (розмір позиції, наявність SL/TP) при кожному fill-івенті та при звірці.
- Залишок вхідного ордера, що не виконався за `entry_timeout_s`, скасовується; позиція лишається з тим розміром, що виконався, під захистом.
- Кількість, середня ціна та комісія беруться з таблиці `fills`.

### 9.4. Збої під час керування захистом

- Втрата зв'язку при зміні SL: журнал помилки, критичне сповіщення в Telegram, **заборона нових входів**, повторні спроби кожні `protection_retry_s`, поки захист не підтверджено.
- Зміна SL (breakeven/trailing — опція) дозволена **лише в бік зменшення ризику**. Віддалення SL заборонено.
- Після закриття позиції менеджер перевіряє, що залишкових умовних/захисних ордерів немає, і скасовує знайдені.

## 10. Протокол Emergency Stop

### 10.1. Тригери

**Область дії:** Emergency Stop запускається для одного акаунта (`emergency_runs.account_id`) або для всіх акаунтів одразу (окрема кнопка «Зупинити все»). Тригери: кнопка в UI; Risk Engine (`HALTED` акаунта); критична помилка, яку не вдалося відновити (наприклад, не вдається встановити SL після повторів); команда з Telegram (опція, з підтвердженням).

### 10.2. Властивості

Процедура **не атомарна** (між біржею та БД атомарності немає), натомість вона **ідемпотентна, відновлювана після перезапуску та виконується циклом до досягнення цільового стану**: на біржі 0 позицій і 0 відкритих ордерів по символах ботів відповідного акаунта (або всіх акаунтів).

### 10.3. Послідовність

1. Запис у БД `system_state = EMERGENCY_STOP` для акаунта (або всіх) з `emergency_run_id`; `RiskGate` блокує будь-які ордери, що збільшують експозицію на цьому акаунті.
2. Скасування всіх **вхідних** (не `reduceOnly`) ордерів.
3. Закриття кожної позиції ордером `reduceOnly` market. SL/TP **поки лишаються активними** як страховка, доки позиція не підтверджено закрита.
4. Верифікація через REST (і WS): розмір кожної позиції = 0. Якщо ні — повтор кроку 3 (до `emergency_max_attempts`, далі ескалація). За неможливості market-закриття — агресивний limit IOC.
5. Скасування решти захисних/умовних ордерів; верифікація: відкритих ордерів немає.
6. Збереження звіту (позиції, fills, PnL, помилки) та сповіщення в Telegram.

### 10.4. Стійкість до збоїв

- Кожен крок і його результат пишуться в `emergency_runs`/`emergency_steps`. Після рестарту бекенд бачить активний `EMERGENCY_STOP` і **продовжує цикл** з потрібного кроку, не чекаючи звірки.
- Біржа недоступна: повтори з backoff, нагадування в Telegram кожні `emergency_alert_interval_s`. Біржовий SL лишається останнім захистом.
- Вихід зі стану — **лише вручну**, після чистої звірки та підтвердження в UI.

## 11. State Reconciliation

### 11.1. Обов'язкова звірка при старті

Боти в `STARTING` не стають `RUNNING`, поки не виконано:

1. завантаження відкритих позицій та ордерів з біржі (REST);
2. порівняння з БД за таблицею правил (11.4);
3. перевірка плеча, режиму маржі та режиму позицій;
4. перевірка/відновлення SL для кожної відкритої позиції;
5. догрузка пропущених свічок і fills за період простою;
6. перевірка часу (розділ 4.3).

### 11.2. Періодична звірка

- **Основний канал** — приватний WebSocket біржі (order, execution, position, wallet). Реконект із перевіркою пропущених подій через REST.
- **Страховка** — REST-звірка кожні 15–30 с (налаштовується) і додатково після кожного `SUBMISSION_UNKNOWN`.

**Розрив приватного WebSocket (з відкритою позицією або без неї):**

1. Розрив визначається за ping/pong-таймаутом або за відсутністю будь-яких повідомлень довше `ws_stale_s` (за замовчуванням 30 с).
2. Усі боти акаунта переходять у `RECONCILING` (розділ 6.1): нові входи заборонені, дозволені лише керування захистом і закриття позицій.
3. Паралельно виконуються реконект (backoff з jitter) і негайна REST-звірка позицій та ордерів за правилами розділу 11.4; пропущені fills дозавантажуються через `fetch_executions`.
4. Після успішної звірки та відновлення підписок (order, execution, position, wallet) боти повертаються в `RUNNING`.
5. Якщо звірка не вдається довше `reconcile_escalation_s` (за замовчуванням 60 с), надсилається критичне сповіщення в Telegram. Весь цей час позиція захищена біржовим SL.

### 11.3. Принцип

Біржа — джерело істини для **фактів**. Але **невідома позиція не «усиновлюється» мовчки** — система шукає причину та просить рішення людини.

### 11.4. Правила розбіжностей

| Розбіжність | Дія |
| --- | --- |
| Ордер на біржі з префіксом `tb` + **наш** `HOST_ID`, якого немає в БД | імпорт як `orphan`, сповіщення |
| Ордер на біржі з префіксом `tb` + **чужий** `HOST_ID` | акаунт торгується з іншого комп'ютера: усі боти акаунта `PAUSED` (`FOREIGN_HOST_ORDERS`), CRITICAL; ордер не чіпати |
| Ордер без префікса (поставлено вручну) на символі бота | не чіпати, сповіщення |
| Позиція на біржі за символом бота, у БД немає | символ `PAUSED`, критичне сповіщення; у UI кнопки «Прийняти під керування» (з розрахунком SL) та «Закрити» |
| Позиція в БД, на біржі немає | закрити запис як `CLOSED_EXTERNALLY`/спрацював SL; PnL — із завантажених fills |
| Розмір позиції відрізняється | взяти розмір біржі, перевірити SL, сповіщення |
| На позиції немає SL | негайно виставити (найвищий пріоритет), інакше політика розділу 9.2 |
| Плече/маржа відрізняються від конфігу | виправити; якщо не вдається — `PAUSED` |

Додаткове правило періодичної звірки: позиція старша за `horizon_bars` повторно закривається за time-stop (розділ 6.6).

## 12. Моніторинг, сповіщення та робота локально

- **Telegram:** рівні `INFO` (відкрито/закрито угоду), `WARNING` (drift, пропуск даних, reconnect), `CRITICAL` (немає SL, `SUBMISSION_UNKNOWN` довго, Emergency Stop, HALTED, розбіжність позицій). Критичні сповіщення повторюються кожні `critical_repeat_s` (за замовчуванням 300 с), доки стан триває і доки ви не підтвердите сповіщення кнопкою «Підтвердити» в Telegram (inline-кнопка) або в UI. Підтвердження зупиняє лише повтори, а не захисні дії.
- **Dead-man's switch:** бекенд раз на 60 с надсилає heartbeat на зовнішній сервіс (наприклад, Healthchecks.io). Якщо ПК вимкнувся, зник інтернет або процес завис, сервіс сам надсилає тривогу. Це єдиний спосіб дізнатися про збій, коли бот мовчить.
- **Автозапуск:** бекенд і колектор даних (розділ 4.4) працюють як служби з автоперезапуском: Windows — Task Scheduler / systemd у WSL2 (розділ 12.1); macOS — launchd (розділ 12.1.1). Кожен запуск бекенду починається зі звірки (розділ 11.1).
- **Логи:** структуровані (JSON), ротація; окремі канали для торгових рішень, ордерів та помилок.
- **UI:** стан ботів, останній heartbeat і затримка даних, статус Risk Engine, відкриті позиції зі станом захисту, журнал рішень.

### 12.1. Середовище запуску (Windows + WSL2)

Якщо ПК працює на Windows, бекенд, воркер і TimescaleDB запускаються **всередині WSL2 (Ubuntu) або в Docker-контейнерах**, а не у нативній командній стрічці Windows. Це дає повну сумісність Python-пакетів, доступність `uvloop` (не підтримується на нативній Windows) та простіший CUDA-стек.

- **GPU (відкладено, розділ 5.6):** коли знадобиться — драйвер NVIDIA встановлюється у Windows (не в WSL), а CUDA-збірки XGBoost і PyTorch — у WSL2; сумісність RTX 5070 перевіряється окремою задачею.
- **Автозапуск:** запуск WSL2 і служби бекенду через Windows Task Scheduler. Кожен запуск починається зі звірки (розділ 11.1). WSL2 і всі процеси зупиняються при перезавантаженні Windows, тому серверний SL і dead-man's switch обов'язкові.
- **Живлення:** вимкнути сон і гібернацію, план живлення «висока продуктивність».
- **Windows Update:** задати активні години й вимкнути автоматичне перезавантаження. Windows усе одно може перезавантажитись, і це покривають біржовий SL, dead-man's switch та звірка при старті.
- **Час:** увімкнена автоматична синхронізація годинника Windows; розбіжність з біржею контролюється (розділ 4.3).
- **Файли:** дані БД лежать у volume Docker/WSL, а не на диску Windows (`/mnt/c`), щоб уникнути повільного вводу-виводу.

### 12.1.1. Середовище запуску (macOS)

- TimescaleDB — у Docker Desktop (або OrbStack) з іменованим volume; бекенд, воркер і колектор — нативно (Python 3.11+ через `uv`), `uvloop` підтримується.
- **Автозапуск:** служби launchd (`~/Library/LaunchAgents`, `KeepAlive=true`, `RunAtLoad=true`) для бекенду і колектора; Docker Desktop — «запускати при вході».
- **Живлення:** для 24/7 — заборона сну (`sudo pmset -a sleep 0 disablesleep 1` або `caffeinate -s` у службі); ноутбук із закритою кришкою засинає без зовнішнього монітора й живлення — врахувати.
- **Час:** автоматична синхронізація часу macOS увімкнена; розбіжність з біржею контролюється (розділ 4.3).
- **GPU:** не застосовується (CUDA на macOS немає); ML працює на CPU (розділ 5.6).
- Якщо Mac не працює 24/7 — він використовується для розробки і Demo/Testnet, а Live — лише на комп'ютері, що працює постійно (розділ 6.4).

### 12.2. Docker і резервні копії

- У `docker-compose.yml` для TimescaleDB: `restart: unless-stopped`, `healthcheck` (`pg_isready`) та іменований volume для даних.
- **Резервні копії:** `pg_dump` за розкладом (щодня); зберігати 7 щоденних і 4 тижневі копії **на іншому диску**, ніж база. Задачу запускає планувальник ОС або фонове завдання бекенду.
- **Перевірка відновлення:** раз на місяць копія розгортається в тестову БД, звіряється кількість свічок і ордерів.
- Копії `models/` та `.env` зберігаються окремо (розділ 14).

| **Demo** | перевірка логіки на реальних цінах; тривалі прогони нових моделей | Bybit Demo Trading: окремий демо-акаунт із віртуальними коштами, REST `api-demo.bybit.com`, приватний WS `stream-demo.bybit.com`; публічні дані — ті самі, що на mainnet. Той самий адаптер Bybit, що й для live. Обмеження: ордери зберігаються 7 днів, не всі ендпоінти доступні (перелік перевіряється на етапі 3, задача T3.7) |
| **Testnet** | **обов'язковий** етап перед live: chaos-сценарії й 7-денний прогін | окремий тестовий ринок біржі з власними (неліквідними) цінами: перевіряє state machine, часткові fills, SL, Emergency Stop, реконекти. Перевіряє **механіку, а не прибутковість** (розділ 5.3) |
| **Live** | реальна торгівля | старт із мінімальним розміром; підвищення розміру лише після проходження критеріїв розділу 18 |

- Власного симулятора виконання (Paper) у проєкті немає: Demo дає реальні ціни й реальну поведінку API біржі без власного коду симуляції. Chaos-сценарії й 7-денний прогін лишаються на Testnet.
- Режим бота фіксується при створенні; Demo і Testnet приймають моделі зі статусом CANDIDATE або APPROVED, Live — лише APPROVED. Перемикання на Live — лише через зупинку бота та явне підтвердження; ключі Live, Demo та Testnet — окремі змінні в `.env`.
- Ордери різних режимів (`demo`, `testnet`, `live`) ніколи не змішуються в одних таблицях без поля `mode`.

## 14. Безпека

- **Ключі біржі:** лише право торгівлі, **без права виводу**; IP whitelist, якщо IP статичний. Для бота доцільно окремий субакаунт із обмеженим балансом. Це і є основний захист: навіть викрадений ключ не дає вивести кошти.
- **Зберігання ключів:** у файлі `.env` (змінні `BYBIT_<MODE>_API_KEY` / `BYBIT_<MODE>_API_SECRET` для `DEMO`, `TESTNET` і `LIVE`; демо-ключі створюються в демо-акаунті Bybit), права доступу лише власника (`chmod 600`), файл не потрапляє в git. Шифроване сховище в БД і UI для введення ключів **не використовуються**: ключ шифрування лежав би на тому ж диску, тож реального захисту воно не додає (`docs/decisions/0002-keys-in-env.md`). Зміна ключа — правка `.env` і перезапуск бекенду.
- **Перевірка при старті:** бекенд запитує дозволи кожного ключа через API біржі й **не запускає ботів цього режиму**, якщо в ключа є право виводу. Результат перевірки і час зберігаються в `exchange_accounts`. Якщо API не дозволяє перевірити — критичне попередження і ручне підтвердження (розділ 19).
- **Секрети в коді:** лише як `SecretStr`; ніколи не потрапляють у логи, API-відповіді та UI (маскування).
- **Локальний API:** слухає лише `127.0.0.1` (порт `API_PORT`, адреса не налаштовується). Через те, що будь-яка веб-сторінка в браузері може звертатися до localhost, потрібні: bearer-токен для UI (`API_TOKEN` у `.env`, щонайменше 32 символи; без нього торговий процес не стартує; потрібен для всіх ендпоінтів, включно з health і схемою OpenAPI), перевірка заголовків `Host` (лише `127.0.0.1`/`localhost` з портом API) і `Origin` (лише з `API_ALLOWED_ORIGINS`) — інакше 403, суворий CORS (лише loopback-origins UI, без credentials). Інтерактивна документація API (Swagger UI, ReDoc) вимкнена, бо вантажить сторонній JS. Це захищає від CSRF та DNS rebinding (`docs/decisions/0007-local-api.md`).
- **Небезпечні дії** (запуск Live, послаблення ризиків, вихід із `EMERGENCY_STOP`) потребують явного підтвердження та пишуться в аудит-журнал.
- **Резервні копії:** щоденний `pg_dump`, копія `models/`; `.env` — окремо, у менеджері паролів або іншому зашифрованому сховищі, не разом із дампами БД.
- **Залежності:** закріплені версії (lock-файли), `.env` не потрапляє в git.

### Облік капіталу, виплат та інструментів

| Таблиця | Призначення |
| --- | --- |
| `equity_snapshots` | `account_id`, час, equity, баланс, нереалізований PnL, `peak_equity`, `day_start_equity`. Запис раз на хвилину та після кожного fill; equity береться **з біржі**, а не рахується локально |
| `ledger` | `account_id`; журнал транзакцій біржі: комісії, funding, реалізований PnL, поповнення та виведення. Дедуплікація за id події |
| `instruments` | tick size, крок кількості, мінімальна кількість і номінал, максимальне плече, статус, час оновлення |

- Денний збиток = `(equity − day_start_equity) / day_start_equity`; просадка = `(peak_equity − equity) / peak_equity`.
- Поповнення та виведення з `ledger` коригують `peak_equity` і `day_start_equity`, інакше внесок хибно зменшить просадку, а виведення хибно її збільшить.
- Чистий PnL = реалізований PnL + funding − комісії.
- `instruments` оновлюється при старті, раз на добу та після відхилення ордера через фільтри біржі. Ціни округляються до tick size, кількість — вниз до кроку, плече = менше з конфігу та біржового максимуму.
- Якщо статус інструмента не «торгується» (зупинка торгів, делістинг), бот переходить у `PAUSED`, нові входи заборонені, SL лишається на біржі, надсилається сповіщення.

## 16. API

- REST (FastAPI, pydantic v2) із автогенерацією OpenAPI та TypeScript-типів для фронтенду.
- Групи: `/data` (backfill, пропуски), `/models` (jobs, метрики, approve), `/bots` (create/start/pause/stop, ручні тести `[Test Long]`/`[Test Short]` — лише Demo/Testnet), `/positions`, `/orders`, `/risk` (конфіг, статус), `/system` (emergency-stop для акаунта або для всіх, reconcile, health, статус перевірки ключів — лише результат, без самих ключів).
- WebSocket-канали: `bots`, `positions`, `orders`, `jobs`, `alerts` (з підтвердженням CRITICAL), `prices`.
- Усі змінюючі команди ідемпотентні і повертають зрозумілі коди помилок. Кожен `POST`/`PUT`/`PATCH`/`DELETE` потребує заголовка `Idempotency-Key` (без нього — 400): повтор з тим самим ключем повертає збережену відповідь і не виконує дію вдруге; інший запит з тим самим ключем — 422; запит, результат якого невідомий (збій обробника або процесу), — 409 і повторно з цим ключем не виконується (людина перевіряє стан і робить нову дію). Помилки — у єдиному форматі `{"error": {"code", "message"}}` зі стабільними кодами (`docs/decisions/0007-local-api.md`).

## 16А. Вимоги до веб-інтерфейсу: підказки (Tooltip / Popover)

Інтерфейс має бути зрозумілим без досвіду в трейдингу та ML. Біля кожного налаштування, поля форми, колонки таблиці, метрики та статусу є підказка, що це означає простими словами.

### 16А.1. Два рівні підказок

| Рівень | Коли використовується | Поведінка |
| --- | --- | --- |
| **Tooltip** | короткі пояснення: колонки, статуси, іконки, метрики | з'являється при наведенні та при фокусі з клавіатури; 1–2 речення |
| **Popover** | складні налаштування та небезпечні дії | відкривається кліком на іконку ⓘ (або Enter); закривається Esc або кліком поза ним; містить розгорнуте пояснення |

### 16А.2. Зміст Popover

Кожен Popover має однакову структуру:

1. **Що це** — одне речення простими словами.
2. **Приклад** — із конкретними числами.
3. **Значення за замовчуванням і допустимий діапазон.**
4. **Що станеться, якщо збільшити або зменшити.**
5. **Попередження** — лише для ризикових параметрів (плече, ліміти, Live-режим, Emergency Stop).

Приклад для `risk_per_trade_pct`: «Яку частину капіталу ви готові втратити в одній угоді, якщо спрацює стоп-лосс. При капіталі 1000 USDT і значенні 0,5% максимальний збиток на угоду — 5 USDT. За замовчуванням 0,5%, діапазон 0,1–2%. Більше значення дає більші прибутки й більші збитки; значення вище 2% небезпечне.»

Для числових полів, де це можливо, Popover показує **живий розрахунок** за поточними значеннями (наприклад, максимальний збиток у USDT за поточним капіталом).

### 16А.3. Де підказки обов'язкові

- **Risk Engine:** усі параметри з розділу 8.2.
- **Налаштування бота:** символ, таймфрейм, режим (Demo / Testnet / Live), модель (з неї беруться первинна стратегія, `min_edge` і `min_confidence` — окремо в боті не змінюються), `max_hold_bars`.
- **ML Studio:** параметри таргета (`tp_atr_mult`, `sl_atr_mult`, `horizon_bars`), первинна стратегія, діапазони Optuna, кількість спроб, `min_edge`, `min_confidence`, DSR, PBO, коридор результатів, кількість відкриттів hold-out, метрики результатів.
- **Метрики:** profit factor, просадка, Sharpe, hit-rate, ймовірність `p`, очікувана вигода EV, результат у R, DSR, PBO, PSI/drift.
- **Статуси** ботів, ордерів і позицій (`PAUSED`, `SUBMISSION_UNKNOWN`, `ENTRY_FILLED_UNPROTECTED` та інші): що це означає і що робити.
- **Ключі API:** статус перевірки дозволів кожного режиму; які права потрібні, чому не можна давати право виводу, як замінити ключ (`.env` + перезапуск).
- **Небезпечні дії:** запуск Live, Emergency Stop, вихід з `EMERGENCY_STOP`, послаблення лімітів.
- **Графік:** легенда позначок угод, SL/TP, ціни входу.

### 16А.4. Реалізація

- **Єдине джерело текстів** — файл довідки (ключ → `short`, `long`, `example`, `default`, `range`, `warning`), українською. Тексти не вшиваються в компоненти.
- Один компонент `<FieldHelp id="…" />` для всіх полів, щоб поведінка була однаковою.
- Значення за замовчуванням і діапазони підтягуються зі схеми API (OpenAPI), щоб довідка не розходилася з бекендом.
- **Автоперевірка:** тест у CI падає, якщо поле конфігурації з бекенду не має запису у файлі довідки.
- **Доступність:** підказки працюють з клавіатури, мають `aria-describedby`, не зникають, поки на них наведено курсор чи фокус; на сенсорних екранах відкриваються по дотику.

## 18. Тестування та критерії приймання

### 18.1. Обов'язкові автотести

- **Look-ahead:** фічі для свічки `t` не змінюються, якщо змінити дані після `t-1`.
- **Машина станів:** кожен дозволений і недозволений перехід; відновлення з `SUBMISSION_UNKNOWN`.
- **Risk Engine:** розрахунок розміру, ліміти, ліквідаційна відстань, граничні значення лотів.
- **Ідемпотентність:** повторна обробка тієї самої свічки та дублікат fill-події не створюють подвійних ордерів і fills.

* **Parity бектесту та live:** `calc_position_size()`, модель витрат і функції лімітів `risk/limits.py` дають однаковий результат у бектестері та в `RiskGate` на однакових даних.
* **ML-конвеєр:** взаємовиключність LONG/SHORT у двосторонній розмітці; правило гепу й песимістичне OHLC у симуляторі; ваги унікальності на синтетичних перекриттях; purging за часом для всіх символів; look-ahead для старших таймфреймів і даних деривативів; DSR/PBO на синтетичних даних з відомим результатом; правило EV на граничних значеннях; заборона `CANDIDATE` при `git_dirty`; блок інференсу при розбіжності версії бібліотеки; перемішані мітки дають результат ≈ 0.

### 18.2. Chaos-сценарії (Testnet)

1. `kill -9` процесу між записом `SUBMITTING` і відповіддю біржі.
2. Обрив мережі під час відправки ордера та під час зміни SL.
3. Дубльовані та пропущені WS-події; реконект WS.
4. Часткове виконання входу, далі скасування залишку.
5. Помилка встановлення SL → примусове закриття.
6. Ручне закриття/відкриття позиції на біржі → правила розділу 11.
7. Emergency Stop із перезапуском бекенду посередині.
8. Зсув годинника, недоступність Telegram, 429 від біржі.
9. Той самий акаунт запущено з другого комп'ютера: чужий `HOST_ID` в ордерах → `PAUSED` (`FOREIGN_HOST_ORDERS`); бот на недозволеному комп'ютері не стартує.

### 18.3. Критерії приймання перед Live

- усі автотести та chaos-сценарії пройдені;
- Testnet ≥ 7 днів без втрачених ордерів, подвійних позицій та позицій без SL;
- модель має статус `APPROVED` (розділ 5.3), коридор результатів (розділ 5.7) записаний у метадані й активний;
- Telegram та dead-man's switch перевірені навмисним вимкненням бекенду;
- ключ без права виводу, UI доступний лише локально;
- стартовий розмір не більше 10–20% від запланованого, ліміти розділу 8 активні.

* кожне поле, метрика та статус у веб-інтерфейсі має підказку (розділ 16А), автоперевірка в CI проходить.

## 19. Параметри для узгодження перед стартом

- Торговий символ і таймфрейм першого бота (рекомендація: BTC, 1h); список `research_symbols` для навчання (5–8 символів).
- Первинна стратегія (1–2 правила) для meta-labeling; `min_trades_per_fold`, пороги DSR і PBO, `min_edge`.
- Стартовий капітал та значення лімітів Risk Engine (розділ 8.2).
- Тип акаунта Bybit (Unified Trading Account) і наявність окремого субакаунта.
- Комп'ютери: `HOST_ID` для Windows-ПК і Mac; який комп'ютер дозволений для кожного акаунта (`allowed_host_id`); на якому працює Live 24/7. Обліковий запис Telegram-бота; зовнішній сервіс для heartbeat.
- Параметри таргета: множники ATR і `horizon_bars`.

**Припущення про Bybit, які перевіряються на Testnet до Live:**

- чи біржа відхиляє повторний `clientOrderId` (на цьому тримається ідемпотентність);
- чи API дозволяє перевірити, що в ключа немає права виводу (інакше це перевіряється вручну);
- як поводяться прив'язані TP/SL при частковому виконанні входу;
- актуальні комісії, а також формат і довжина `orderLinkId`;
- тип виконання TP/SL у режимі `Full` (market) і фактичний slippage на стопах;
- які з потрібних ендпоінтів і WS-потоків доступні в Demo Trading (ордери, trading-stop, позиції, execution list, приватний WS, перевірка дозволів ключа);
- глибина історії open interest, premium index і long/short ratio; формат WS-потоку ліквідацій.
